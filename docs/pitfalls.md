## 坑 0 · 假数据一眼假 ✅（2026-10-24 补证据）

**我原以为**：造点数据用 `Math.random()` 就够了，反正曲线都长得差不多。

**其实是**：`random()` 画出来是**锯齿**——相邻两点可以不相关，采样间隔精确到毫秒，一眼假。真设备的值至少有四层质感：**惯性**（一阶低通）、**缓慢漂移**、**偶发尖峰**、**采样抖动**。

**证据 1（数值层面）**：`TempSignal` 用 `v = 0.95v + 0.05·(基准 + 3·sin(2πt/180s) + N(0, 0.08))`，0.5% 概率单点跳 6~12℃；从站每周期打印，10 秒里从 62.01 → 62.26℃ **缓慢爬升**，不是跳变：

```
[19:25:42.087] unit=1  temp=  62.01°C runtime=   1234.50 h motor=false alarm=false
[19:25:45.111] unit=1  temp=  62.06°C runtime=   1234.50 h motor=false alarm=false
[19:25:50.103] unit=1  temp=  62.22°C runtime=   1234.50 h motor=false alarm=false
```

**证据 2（图形层面，2026-10-24）**：页面上 `sim-06` 的 10 分钟曲线（536 点）能同时看到三种形态 ——
**缓慢漂移**（60→65 的爬升）、**惯性回落**（尖峰后指数衰减）、**单点尖刺**（冲到 75℃ 又掉到 55℃）。
这正是"随机数做不到、真设备才有"的质感。

采样间隔也是 **1000 ms ±20 ms 抖动**（`SimSlaveMain`），不是精确的 1.000 s。

> 📌 **为什么值得做**：面试时如果曲线是锯齿，对方会立刻判断"这是编的"；
> 有了尖峰/漂移/抖动，才敢说"我知道真信号长什么样"。

## 坑 1 · 寄存器字序（最经典）✅

**我原以为**：Float32 占两个寄存器，读出来拼一下就是值。

**其实是**：Modbus 只规定「寄存器是 16 位」，**不规定** 32 位值怎么拆。同一份报文，四种约定解出四个数，其中**只有一种**是温度。国内仪表常见 **CDAB**（两个寄存器互换）。

**证据**（`ProbeMain` 实测，同一帧 `reg[0]=0x544E, reg[1]=0x4278`）：

```
== temperature（Float32 = reg[0] + reg[1]）按四种字序解析 ==
  ABCD             3.5435e+12  （不像温度）
  CDAB                  62.08  <== 落在 10~100℃ 区间
  BADC             8.9116e+08  （不像温度）
  DCBA             1.5764e+34  （不像温度）
```

**记法**：读出来是 `1e34` / `1e12` 这种天文数字，基本就是字序错了，不用怀疑设备坏了。
`WordOrder` 枚举把 ABCD / CDAB / BADC / DCBA 四种都实现了，编码解码对称（`registersOf` / `floatOf`），从站和采集端共用同一套。

**顺带一条**：同一台设备的**不同点位可以字序不同**。我们把 `temperature` 设成 CDAB、`runtime_hours` 设成 ABCD，所以采集端必须**按点位配置**字序，不能全局假设一种。

### 已落地：字序是配置项，不是代码常量

真设备不会告诉你它用哪种字序，所以点表里每个点位单独配 `order`（`collector/src/main/resources/points.properties`）：

```properties
device.sim-01.point.temperature.type=float32
device.sim-01.point.temperature.order=CDAB      # 换一台表只改这一行
```

两次证伪都做了：

| 试验 | 结果 | 说明 |
|---|---|---|
| 从站 `--base-temp 25`，点表 `CDAB` | **25.06℃** | 没有隐藏的硬编码值；换个量程就跟着变 |
| 同一台设备，点表只把 order 改成 `ABCD` | **-15222668117814542000.00℃** | 配置真的在驱动解码，不是摆设 |

第二条尤其值得记：**字序配错时程序不会报错**，只会给你一个天文数字然后若无其事地标 GOOD。所以后面应当给点位加**量程校验**（`min`/`max`，超范围判 BAD）—— 光靠"看起来不对"是发现不了的。

## 坑 2 · 40001（1 基惯用编号）vs offset 0（协议 0 基）✅（2026-10-24 实测）

**我原以为**：`40001` 就是报文里的地址。

**其实是**：`40001` 是**惯用编号**（1 基，给人看的），报文里传的是 **offset 0**（0 基）。差一位，整体错位。

**证据 1（正常读取，同时标出惯用编号）**：`ProbeMain` 刻意用 `readMultipleRegisters(unitId, 0, 4)`，打印时两种编号并列：

```
  reg[0] (40001) = 0x544E   21582
  reg[1] (40002) = 0x4278   17016
```

**证据 2（真把 40001 当地址传进去）**：把点表里 `temperature` 的 `offset` 改成 **40001**，其它不动：

```powershell
collector\run-collect.cmd --points D:\iiot-data\bad-offset.properties --cycles 2
```

结果 —— **从站不回包，超时，判 BAD**（不是读到错值，而是根本没响应）：

```
[11:49:06] sim-01  BAD  temperature=--(BAD)°C
    ↳ 读失败：Executing transaction 00 05 00 00 00 06 01 03 9C 41 00 02 failed (tried 5 times)
              Socket timeout reading response - Read timed out
    ↳ 从未读到过好值 → BAD（值不可用，不是 0）
```

**关键就在报文里那两个字节：`9C 41` = 0x9C41 = 40001。**

> 📌 j2mod 老老实实把 40001 当成地址发出去了，从站那边地址越界（它的寄存器只到 offset 3），
> 于是**不响应** → 客户端重试 5 次 → 超时。
> **注意现象形态：不是"读到了错误的值"，而是"一直超时"。**
> 这一点很有用 —— 如果现场调一台表一直超时，而地址"看起来是对的"，就要怀疑 **1 基 / 0 基搞混**。

**对照组（offset=0）**：同一份点表只改回 `0`，立刻正常读出 4 个点。

## 坑 3 · 断线不是 0，是「过期」✅

**我原以为**：设备离线，采集端读不到，那就记 0 / 记 null。

**其实是**：记 0 会被下游当成**真值**——「温度 0℃」比「没有数据」危险得多（操作工会去现场看，或者触发错误的联锁判断）。正确做法是**质量码**：`GOOD` 是真读到的；`STALE` 是读失败但保留上次值；`BAD` 是连上次值都没有。值可以是旧的，但**必须标"这是旧的"**。

**证据**：采集跑着的时候把从站停掉（等于拔网线）。前 5 轮 GOOD，第 6 轮开始 STALE，值**保留 62.18 而不是变 0**，并且带"上次好值"的时刻：

```
[19:33:22.282] sim-01   GOOD  temperature=62.18°C ...
[19:33:23.733] sim-01   STALE temperature=62.18(STALE)°C runtime_hours=1234.00(STALE)h motor_running=false(STALE) alarm=false(STALE)
           ↳ 读失败：从 sim-01@127.0.0.1:1502/unit=1 读取失败: Connection refused: getsockopt
           ↳ 值保留上次、标 STALE（不是 0）；上次好值 19:33:22.282
```

从没读到过好值的时候判 `BAD`，值是 `--`，也不补 0。

**还没撞的部分**：**连接还在、但读超时**的 STALE（设备卡死不回包）。现在从站不回包时连接会被判失效并重连，要演"半死"状态得给从站加 `--hang` 开关（下一步）。

## 坑 4 · 写操作不幂等 🟡（**本 demo 的结构决定了测不出来，诚实说明**）

**我原以为**：写失败就重试，跟 HTTP 一样。

**其实是**：Modbus 写操作**没有幂等保证**。超时后重发可能让执行机构**动作两次**。
工控不能照搬 HTTP 的"失败就重试"。

**证据（能测的那部分）**：写线圈 + 读回确认是对的 —— `ACK=true`，读回 `motor_running = true`：

```
== 写线圈（FC05）
  motor_running <= true  ACK=true  耗时 1 ms
  读回确认 motor_running = true
```

### 为什么本项目测不出"重发导致动作两次"

我们的可写点位只有 **`motor_running`（线圈）**，而 `FC05` 写线圈是**置位语义**：

```
把线圈写成 true  →  写 1 次和写 10 次，结果都是 true   ⇒ 天然幂等
```

**真正危险的写有另外两种形态，本 demo 都没有**：

| 形态 | 例子 | 为什么危险 |
|---|---|---|
| **自增 / 累加型寄存器** | `产量计数 += 1` | 重发 ⇒ 多计一次，数据永久错 |
| **触发型（write-to-trigger）** | 写 1 到 `CMD` 寄存器 ⇒ 启动一次配方下发 | 重发 ⇒ 启动两次，**物理动作两遍** |

### 要做出来需要什么

1. 从站加 `--drop-write-ack`：收到写请求、**真的执行了**，但**故意不回 ACK**
2. 点表里加一个**自增型**或**触发型**点位（例如 `batch_trigger` HOLDING）

这样客户端超时 → 重试 → 从站再执行一次 → 就能看到"动作两次"的后果。

> 📌 **本 demo 的诚实结论**：**知道这个坑、知道它长什么样、知道怎么复现，但没在代码里制造它。**
> 面试时说"我们这个 demo 的写点位是置位语义，天然幂等，所以我没把它做成实验"——
> 比硬说"我测过"要可信得多。

## 坑 5 · 单设备拖垮采集 ✅（2026-10-24 实测）

**实测方式**：100 台并发采集跑起来，然后把从站进程直接杀掉（等于所有设备同时离线）。

**实测输出（20 台 × 24 秒，第 8 秒杀从站）**：

```
[10:31:31]  · 3s  GOOD 240 / 期望 240（100.00%）· STALE 0   · BAD 0 · 80 点/秒
[10:31:34]  · 6s  GOOD 480 / 期望 480（100.00%）· STALE 0   · BAD 0 · 80 点/秒
[10:31:37]  · 9s  GOOD 640 / 期望 720（88.89%） · STALE 80  · BAD 0 · 71 点/秒   ← 杀从站
[10:31:40]  · 12s GOOD 640 / 期望 880（72.73%） · STALE 240 · BAD 0 · 53 点/秒
[10:31:52]  · 24s GOOD 640 / 期望 1040（61.54%）· STALE 400 · BAD 0 · 27 点/秒
```

**结论（三件事同时成立）**：

| 现象 | 说明 |
|---|---|
| **STALE 而不是 0** | 坑 3 的解法在**多设备并发**下同样成立：断线时值保留上次好值、打过期标记 |
| **BAD = 0** | 因为所有设备在断线前都读到过好值 —— 与「从没读到过 = BAD」的规则一致 |
| **采集器没崩** | 20 条虚拟线程全部活到 24s 收工；处理了 **100 轮通信失败**，退出码 0 |

**另外三个可量化的事实**：

- **完整率从 100% 掉到 61.54%** —— 这就是"设备离线"对数据完整性的**量化影响**，比说"有影响"强
- **P95 从 2.15ms 恶化到 469ms、P99 到 685ms** —— 断线时连接超时把延迟分布拉长，**这是监控该看的指标**
- **退避生效**：失败后 GOOD 不再增长，STALE 每轮只 +80（20台×4点），说明轮询间隔被放大（1×→8×，上限 30s）—— **不给掉线设备继续添乱**

**解法（已落地）**：

| 层 | 做法 |
|---|---|
| **线程隔离** | 每台设备一条**虚拟线程**（JDK 21），一台阻塞不占住别人 |
| **连接/锁隔离** | 每台设备**独立 `TcpModbusDriver` 实例** —— 因为 `read()` 是 `synchronized` 的，共用实例会让 100 台**退化成串行** |
| **时间隔离** | 读超时 `--timeout`（默认 2000ms），"连上但不回包"也会被掐断 |
| **异常隔离** | 设备循环 `catch (Throwable)` 全兜住，一台崩了不影响其他 |
| **失败退避** | 连续失败 1×/2×/4×/8× 周期，上限 30s |

**还有没做的**：从站 `--hang`（连上但永不回包）—— 这样能测出"单台挂死时其他台是否照常"。当前已能证明"全部离线不崩"。

## 坑 6 · 时间基准（时钟漂移 / 时区）✅（2026-10-24 实测）

原以为是"设备时钟慢慢不准"，实际上**第一个撞到的是时区**。

### 实测现象

写入时用的是 **epoch 毫秒**（数字，不带时区），写入时的本地时间约 **11:23**。
从 TDengine 查出来却是：

```json
{"ts": "2026-10-24T03:23:19.306Z", "val": 64.98, "quality": "GOOD", ...}
```

**`03:23` + `Z` ⇒ TDengine 按 UTC 存，查询返回 UTC ISO 串。** 本地是 UTC+8，差 8 小时。

### 为什么这很危险

- 如果前端直接把这个字符串当本地时间画图 ⇒ **整张曲线偏 8 小时**，"刚才"的数据会显示成"凌晨"
- 更隐蔽的版本：只显示 `HH:mm:ss` 时看不出日期差，但**跨零点的数据会错位到前一天**

### 落地做法（已实现）

| 层 | 做法 |
|---|---|
| 采集端 | **用 epoch 毫秒写入**，不传字符串时间 —— 避免"服务器时区 vs 客户端时区"的歧义 |
| 存储 | TDengine 内部按 UTC 存（不可改，这是对的做法） |
| 后端 | 把 UTC ISO **原样透传**，不做本地化（后端不该假设客户端在哪个时区） |
| 前端 | `new Date(iso)` 交给浏览器转本地时区 —— 页面在哪个时区打开就显示哪个时区 |

> 📌 **一句话**：**"时间"在工业系统里要分三层看 —— 设备时钟、存储时区、展示时区。**
> 混在一起就会出现"数据看起来晚 8 小时"这种查一整天的问题。

**还没做的**：设备侧 NTP 对时 + 乱序/迟到数据的处理（真设备到货后才有的问题）。

## 坑 7 · 告警泛滥 ✅（2026-10-24 用真实数据量化）

原以为是"告警太多有点烦"，实际量出来是 **83 倍放大**。

### 实测方式（不改任何代码，直接用库里已有数据算）

阈值取 **65℃**（这批设备常年在 59~75℃ 之间漂移，正好反复跨越阈值）：

| 设备 | 采样点（10 分钟） | 越限采样点 | 真实越限**事件** |
|---|---|---|---|
| sim-02 | 594 | 94（15.8%） | **3** |
| sim-05 | 593 | 296（49.9%） | **3** |
| sim-08 | 593 | 446（75.2%） | **4** |
| **合计** | **1780** | **836** | **10** |

### 结论

```
按「采样点」报警 = 836 条告警
按「连续段/事件」报警 = 10 条告警
放大倍数 = 83.6x
```

推算 **10 台 × 10 分钟**：
- 按「点」报警 ⇒ **≈ 2787 条**
- 按「事件」报警 ⇒ **≈ 33 条**

**⇒ 手机 / 企业微信会被刷爆**。而且真正需要人处理的是那 10 次（或 33 次）事件，剩下 800 多条都是同一次抖动重复报的。

### 正确做法（三条，缺一不可）

| 机制 | 作用 | 参数示例 |
|---|---|---|
| **持续时间去抖** | 越限必须**持续** N 秒才报警 | 持续 30 s |
| **回差（hysteresis）** | 恢复阈值 ≠ 触发阈值，避免在阈值附近反复触发 | 触发 >80，恢复 <75 |
| **分级 + 抑制** | 同一设备同一事件只报一次；按严重程度分通道 | 一级电话、二级企微、三级只记库 |

> 📌 **面试口径**：「单点越限就报警是**外行做法**。工业现场叫 **alarm flood（报警风暴）**，
> ISA-18.2 有专门的规范。核心三条：**持续时间去抖 + 回差 + 分级抑制**。」

### ✅ 已实现并做了 A/B 验证（2026-10-24）

**实现**：`collector/core/AlarmEngine.java` —— 一个**状态机**，不是 if-else：

```
NORMAL ──越限且【持续 N 秒】──▶ ACTIVE(WARNING) ──继续升高──▶ ACTIVE(CRITICAL)
   ▲                                  │
   └────── 回落到【触发值 − 回差】──────┘
```

**四条机制同时生效**（第 4 条常被忽略）：

| # | 机制 | 本 demo 参数 |
|---|---|---|
| 1 | 持续时间去抖 | 越限**持续 5 000 ms** 才报 |
| 2 | 回差 | 预警 >80 恢复 <75；严重 >85 恢复 <80 |
| 3 | 分级 | WARNING / CRITICAL，**升级只报一次**（不重复刷 WARNING） |
| 4 | ⭐ **质量码门禁** | **只对 GOOD 判告警**；STALE/BAD 一律不报 —— 设备掉线后那个"最后值"反复送进来是最烦的假告警 |

**A/B 实测（同一批采样点，同时喂两个引擎，只改配置）**：

> 场景：10 台 · 基准 74℃ · 尖峰概率 10%（模拟现场毛刺：只污染**读数**，不改变物理温度）· 90 秒

| 配置 | 告警条数 |
|---|---|
| **不去抖**（持续 0 ms、回差 0℃） | **86 条** |
| **去抖 + 回差**（持续 5 s、回差 5℃） | **12 条** |
| **效果** | ⭐ **减少 74 条（压掉 86.0%）** |

同期计数：

```
越限采样点     330   （按点报 = 330 条）
阈值穿越        64   （一穿一报 = 64 条）
★ 实际告警     12   （去抖+回差之后）  ⇒ 相对采样点 27.5x，相对穿越 5.3x
```

**事件日志（三种机制都能看到）**：

```
12:41:57 [ALARM]   sim-09 WARNING  80.26  (持续 5.1s)    ← 去抖：撑够 5 秒才报
12:42:03 [UPGRADE] sim-09 CRITICAL 90.37  (持续 11.1s)   ← 分级：升高只报一次
12:42:13 [CLEAR]   sim-09 CRITICAL 70.02  (回差恢复)      ← 回差：掉到 80 以下才清
```

**顺带修了一个仿真模型的错**：原来把尖峰**加进滤波器状态**，10% 概率下会累积，
值稳定在 **~92℃** —— 那就不再是"毛刺"，而是"真的持续超温"，去抖也就失去了可演示的对象。
正确模型：**尖峰只作用在读数上，不写回物理状态**（真实传感器毛刺是"这次读数错了"，
不是"温度真跳了 10℃"）。

> **本 demo 的状态**：✅ **已实现 + 已 A/B 验证**。
> 没做的部分：通知通道（短信/企微/邮件）、同源告警合并（suppression）、值班排班。
