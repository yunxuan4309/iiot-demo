# Modbus TCP 抓包实测（Wireshark）

> 写于 2026-10-30。对应 JD 职责 3「工业软件、控制程序及设备通信网络**运行监测和故障处理**」。
> 抓包文件：`docs/modbus-fc03.pcapng`（真实流量，非构造）

---

## 一、为什么要抓包

**点表配错、字序猜错、超时、从站不响应** —— 这些问题靠"看日志"永远说不清，只有看报文才知道：

- 到底发了什么功能码？起始地址是 0 还是 1？
- 从站是真没回，还是回了异常码？
- 读回来的 4 个字节，按什么顺序拼？

抓包是**南向排障的最终证据**。这也是我能回答"你怎么定位通信问题"的唯一硬答案。

---

## 二、怎么抓的（命令）

```powershell
# 1) 先起仿真从站（标准端口 502，Wireshark 默认就认它）
java -jar collector\target\collector-0.1.0-SNAPSHOT.jar --port 502

# 2) 另一条命令：抓回环上的 502 流量（Npcap 回环网卡）
tshark -i \Device\NPF_Loopback -f "tcp port 502" -a duration:8 -w docs\modbus-fc03.pcapng

# 3) 同时让采集端读几轮，产生流量
java -cp collector-0.1.0-SNAPSHOT.jar com.iiot.collector.CollectMain --points <指向502的点表> --cycles 15
```

结果：**85 个包，其中 43 个是 Modbus**，循环是 `FC01 → FC02 → FC03`（因为我们有 4 个点位分属线圈/离散输入/保持寄存器）。

## 三、跑通这一趟踩的 4 个坑

### 坑 1 · Wireshark 装了，tshark 却抓不了

- **现象**：`tshark -D` 报 `Unable to load Npcap (wpcap.dll)`。
- **真因**：Wireshark 本体 ≠ 抓包驱动。**抓包靠 Npcap**，winget 静默装 Wireshark 时不一定把 Npcap 装上。
- **以后**：单独装 Npcap（npcap.com），装完 `Get-Service npcap` 应为 **Running**。

### 坑 2 · 抓不到 `127.0.0.1` 的流量

- **现象**：网卡列表里没有回环。
- **真因**：Npcap 安装时 **「Support loopback traffic」默认不勾**。
- **以后**：装的时候必须勾上，装完 `tshark -D` 里应出现 `\Device\NPF_Loopback`。

### 坑 3 · ⭐ 端口不是 502，Wireshark 就当它是普通 TCP

- **现象**：抓包文件里全是 `data`，`modbus` 过滤出来 **0 帧**。
- **真因**：Modbus/TCP 解码器**默认只绑 502**。我们用 1502（避开特权端口）时，它不会自动识别。
- **以后**（三选一）：
  1. **抓的时候就用 502**（最省事，本次采用）；
  2. `tshark -d tcp.port==1502,mbtcp` —— 注意解码器名是 **`mbtcp`**，写 `modbus` 会报 *Protocol "modbus" isn't valid for layer type "tcp.port"*；
  3. Wireshark GUI：右键 → **Decode As** → Modbus/TCP。

### 坑 4 · 用 `-d` 绑了还是报「Cannot classify packet type」

- **现象**：能解出功能码，但 Wireshark 提示无法判断是请求还是应答。
- **真因**：`-d` 只把解码器挂到端口上，解码器内部**还要靠端口号区分方向**（请求 → 502 是目的，应答 → 502 是源）。
- **以后**：直接抓 502；或在 GUI 里用 Decode As（它会同时设置双向）。

## 四、报文逐字段拆解（这是核心）

### 请求（帧 9）

```
00 2f | 00 00 | 00 06 | 01 | 03 | 00 00 | 00 04
```

| 字段 | 字节 | 值 | 含义 |
|---|---|---|---|
| 事务标识 Transaction Id | `00 2f` | 47 | 请求/应答配对用（客户端自增） |
| 协议标识 Protocol Id | `00 00` | 0 | 0 = Modbus |
| 长度 Length | `00 06` | 6 | 后面还有 6 字节 |
| 单元标识 Unit Id | `01` | 1 | **从站地址**（RS485 上就是设备地址） |
| 功能码 Function Code | `03` | 3 | 读保持寄存器 |
| 起始地址 Reference Number | `00 00` | **0** | ⚠️ **0 基！** 惯用编号 40001 在这里是 0 |
| 寄存器数 Word Count | `00 04` | **4** | 一次读 4 个寄存器 |

### 应答（帧 11）

```
00 2f | 00 00 | 00 0b | 01 | 03 | 08 | de cc  42 78  00 00  04 d2
```

| 字段 | 值 | 含义 |
|---|---|---|
| 事务标识 | `00 2f` = 47 | 与请求一致（配对成功） |
| 长度 | `00 0b` = 11 | 单元(1) + 功能码(1) + 字节数(1) + 数据(8) |
| 功能码 | `03` | 与请求一致 |
| 字节数 Byte Count | `08` | 4 个寄存器 × 2 字节 |
| 数据 | `de cc 42 78 00 00 04 d2` | 4 个寄存器的原始值 |

### 数据怎么变成工程值（重点）

| 寄存器 | 原始 | 点位 | 字序 | 解出 |
|---|---|---|---|---|
| reg0 + reg1 | `DE CC` `42 78` | temperature (Float32) | **CDAB** | `0x4278DECC` ≈ **62.2 ℃** |
| reg2 + reg3 | `00 00` `04 D2` | runtime_hours (UInt32) | **ABCD** | **1234 h** |

**同一帧、同一台设备，两个点位用了两种字序。**
这就是"字序必须按点位配置、不能全局假设"的**报文级证据** —— 面试讲到这里最有说服力。

> 如果按 ABCD 解温度：`0xDECC4278` ≈ **-7.36e18** —— 典型的"天文数字"，一眼就知道字序错了。

> ⚠️ **但别以为配错就一定"很大"**：另一帧里 `reg0=3188(0x0C74)`、`reg1=17017(0x4279)`，按 ABCD 解出来是 **`1.88e-31` ≈ 0**。
> 也就是说字序配错的结果可能是**天文数字**，也可能是 **0 / 极小值** —— **不能只靠"看着不对"发现**，必须靠**量程校验**（点表 `min`/`max`）或人工核对量纲。这就是点表要支持量程校验的原因。

## 五、这张图在面试里怎么用

> 「排障我不会只看日志。我会抓 Modbus 报文：看功能码对不对、起始地址是 0 基还是 1 基、从站回的字节数和字序。比如这一帧，`FC03` 读 4 个寄存器，回来的 8 个字节里，前两个字按 **CDAB** 才是温度，后两个字按 **ABCD** 才是运行时长 —— 字序配错时数值会变成天文数字。」

**可能被追问**

| 追问 | 回答 |
|---|---|
| Modbus 报文最大多长？ | RTU 上限 **256 字节**（地址1+功能码1+数据252+CRC2）；TCP 多了 7 字节 MBAP 头。所以一次别读太多寄存器，读 100 个就要拆帧。 |
| 为什么有事务标识？ | TCP 上可能乱序/并发，靠 Transaction Id 把应答和请求配对。RTU 不需要，因为一问一答是串行的。 |
| 抓包能看出什么故障？ | 从站不回（只有请求没有应答）→ 地址/波特率/接线；回异常码 `01` → 功能码不支持；`02` → 地址越界；字节数不对 → 从站实现有问题。 |
| 生产环境怎么抓？ | 交换机端口镜像（SPAN）或串口监听；不能随便在被控机上装抓包工具。 |
