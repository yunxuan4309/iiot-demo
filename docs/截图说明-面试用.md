## 一、`GX-D0=40-Y0导通.png`

### 图里有什么

| 位置 | 内容 |
|---|---|
| 标题栏 | `LD-报警测试.gxw - [[PRG]监视 执行中 MAIN (只读) 11步]` |
| 第一步（步 0） | `M8000` 常开触点 → `[CMP D0 K32 M0]` |
| 第二步（步 8） | `-|M0|` → `(Y000)` |
| 数值 | **`D0 = 40`**、**`M0 = ON`** |
| 颜色 | 触点和线圈是**蓝色高亮** |

### 证明了什么

1. **11 步** = 程序已**转换**（F4 通过）；灰底未转换是不能仿真的
2. **「监视 执行中」** = 程序正在**仿真器里运行**（不是静态画图）
3. **`D0=40 → M0=ON`** = `CMP` 比较指令按 FX 语义执行：`40 > 32` 成立
4. **`Y0` 蓝色** = 输出线圈得电

### 怎么讲（口述）

> 「这是三菱 FX3U 的梯形图，11 步，已经转换并在 GX Simulator 里跑起来了。我用 `M8000`（常 ON）给 `CMP` 做母线入口，比较 `D0 > 32`，结果进 `M0`，`M0` 驱动 `Y0`。现在 `D0=40`，所以 `M0=ON`、`Y0` 导通。」

### 可能被追问

| 追问 | 回答 |
|---|---|
| 为什么 `CMP` 前面要挂 `M8000`？ | `CMP` 是**无触点指令**，没有通断状态，不能直接挂母线；`M8000` 是常 ON 特殊继电器，给它做入口。这是三菱的常规写法。 |
| 为什么不用比较触点 `LD>`？ | 也行。我踩过坑：中文输入法把半角 `>` 转全角，`LD>` 被拆成 `LD` 和一个常数接点，转换直接失败。`CMP` 更稳，三种写法我都试过。 |
| 仿真器算真 PLC 吗？ | **不算**。GX Simulator 是 CPU 仿真器，X/Y/D 都是内存里的位和字，没有对外通信口。它能证明逻辑，不能证明链路 —— 数据链路我用 CODESYS 的真运行时做。 |

## 二、`GX-D0=20-Y0断开.png`

### 图里有什么

同一份程序，只把 `D0` 改成 **20**：`M0` 变 **`0`（OFF）**，触点和线圈**回到细线**（蓝色消失）。

### 证明了什么

**反向验证**：`20 > 32` 不成立 → `M0=OFF` → `Y0` 断开。
如果只拍"亮"的那张，别人可以怀疑"是不是强制输出"；两张对照才能说明是**真的在比较**。

### 怎么讲

> 「同一份程序，`D0` 改成 20，`M0` 回 OFF、`Y0` 熄灭。两张对照才说明是逻辑在判断，不是我把输出强制成 ON。」

> ⚠️ 一个小提醒：**GX Works2 用蓝色表示导通**（CODESYS 才是绿色）。别在面试时把"蓝色"说成"变绿"。

## 三、`PLC直读-35.6C-xAlarm-TRUE.png`（最重要的一张）

### 图里有什么

CODESYS 在线视图的变量表：

| 变量 | 值 | 地址 | 含义 |
|---|---|---|---|
| `rTemp` | **35.6** | `%QW0` | PLC 算出的温度（同时暴露给 Modbus TCP 从站） |
| `xAlarm` | **TRUE** | `%QX20.0` | PLC 的判断结果 |
| `wTempIn` | **0** | `%IW0` | 旧路径：Java 写进来的 —— **现在是 0，说明 Java 没参与** |
| `wHumidityRaw` | **612** | `%IW10` | PLC 从串口读到的**原始**湿度寄存器 |
| `wTempRaw` | **356** | `%IW11` | PLC 从串口读到的**原始**温度寄存器 |
| `rHumidity` | **61.2** | — | PLC 算出的湿度 |

### 证明了什么（这是全项目最硬的一环）

1. **采集在 PLC 里**：`%IW10/%IW11` 是 Modbus **RTU 主站**通道读上来的，不是 Java 写的
2. **Java 没参与**：`wTempIn = 0` —— Java 那条写寄存器的链路（`BridgeMain`）根本没开
3. **判断在 PLC 里**：`35.6 > 32` → `xAlarm = TRUE`
4. **原始值到工程值**：`356 ÷ 10 = 35.6`、`612 ÷ 10 = 61.2` —— 这就是国产仪表主流的**「16 位整数 + 缩放 ×0.1」**

### 怎么讲

> 「这是 CODESYS 的在线视图。`%IW10/%IW11` 是 PLC 作为 **Modbus RTU 主站**从串口读回来的原始寄存器：612 和 356；PLC 里 `÷10` 得到 61.2%RH 和 35.6℃。`xAlarm` 因为 35.6 > 32 变成 TRUE。注意 `wTempIn` 是 0 —— 那是以前 Java 喂数据的通道，**现在 Java 完全没参与**，采集和判断都在 PLC 里。」

### 可能被追问（都会问到，先想好）

| 追问 | 回答 |
|---|---|
| **这是真传感器吗？** | **这一张不是**，是虚拟串口对（com0com 的 COM5↔COM6）+ 一个按真协议应答的测试桩（`RtuSlaveMain`），寄存器布局按真表 IKM10000WS01 复刻（offset0 湿度、offset1 温度、×0.1）。插真表只改 COM 号。真表的实测在 `docs/RTU设备接入指南.md §十`。 |
| 为什么要做测试桩？ | 真表会坏、会忙、不能随时改数值。测试桩能**复现任意温度**、验证报警边界和负温，这是工业上标准的"脱机调试"做法。 |
| 为什么温度要用 `INT_TO_REAL(WORD_TO_INT(...))`？ | 温度是 **int16 有符号**，`-5.3℃` 存成 `0xFFCB`。直接 `WORD_TO_REAL` 会得到 65483 → 6548℃。补码这一步不做，冬天就出错。 |
| 那张图左下角 `%IW0` 为什么留着？ | 迁移期的**双路兜底**：主站读不到（=0）时才退回 Java 写进来的值。正式版会删掉。 |
| 串口是独占的吗？ | 是。CODESYS 在线时占着 COM5，我这边再打开同一个口直接报错。所以"PLC 读"和"上位机读"在物理层就是二选一。 |
