工业设备数据采集与在线监测

南向 Modbus（TCP/RTU）→ 统一数据模型（含质量码）→ 时序库 → Web 监测页 · 全链路自建、可一条命令复现

解决什么问题：工业数据与互联网数据的三点差别，也是本项目的三个工程约束 —— ① 数据在二进制寄存器里（32 位值跨两个 16 位寄存器，四种字节序）② 数据可能不可信（断线不能补 0） ③ 点位约定在厂家手册里（地址/类型/字序/量程全走配置，代码里没有设备私有约定）。

八个坑（每条都是「我以为是 X，其实是 Y」）

#坑结论
0假数据一眼假random() 是锯齿；真信号要有惯性（一阶低通）＋缓慢漂移＋偶发尖峰＋采样抖动
1寄存器字序Modbus 只规定寄存器是 16 位，不规定 32 位怎么拆；国内仪表常见 CDAB（字交换）
240001 vs offset 0手册的 40001 是 1 基惯用编号，报文传 0 基。混了不是读错值，而是永远超时（报文里 9C 41 = 40001）
3断线不是 0补 0 比没数据更危险 → 必须显式标 STALE（旧值）／BAD（无值），值可以是旧的但必须标"这是旧的"
4写不幂等超时重发会让"触发型"写执行两次。本 demo 可写点只有线圈置位（天然幂等），故只记录、未制造
5单设备拖垮采集三重隔离：线程（虚拟线程）／连接（每设备独立 driver，因为 read() 是 synchronized）／时间（读超时）＋ 失败退避
6时间基准TDengine 存 UTC、返回带 Z；前端不转时区整张图偏 8 小时。采集端用 epoch 毫秒写入避免歧义
7告警泛滥实测：10 分钟 3 台设备 836 个越限采样点，但只有 10 次真实越限事件 = 放大 83.6 倍；解法＝持续时间去抖 ＋ 回差 ＋ 分级抑制

技术栈与取舍

选择为什么
Java 21 虚拟线程100 台设备＝100 条线程，平台线程太重
j2mod主站＋从站一体，能自己造仿真设备验证协议
纯文本点表厂家点位约定不该写进代码
选择为什么
TDengine工业圈常见；超级表＋子表天然贴合「设备×点位」
REST 而非 JDBC免 native 库、可跨 WSL／SSH 隧道；返回自带 column_meta
ECharts 本地副本离线可跑，不依赖 CDN

边界（诚实的部分）

  • 不是生产系统：单机、无认证、无高可用、无联锁。
  • 真传感器尚未接入：当前用仿真从站验证协议链路；RtuModbusDriver 接口已留，硬件到货只换实现。
  • 北向 MQTT 未实现：页面走 HTTP，架构里预留 iiot/{device}/{point} 的 topic 规范。
  • 告警模块未实现：坑 7 只有设计（去抖＋回差＋分级），没有代码。
  • 只有 4 个点位：够验证链路，不够覆盖真实产线（一台设备常几十上百点位）。
