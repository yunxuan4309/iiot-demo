# 让 PLC 自己读传感器：从三菱仿真器到 CODESYS 软 PLC 的一次改造

> 我最初的做法很"互联网"：**Java 直接读 485 传感器**，PLC 在旁边做个报警逻辑"演一下"。
> 后来意识到这套东西**在工业上讲不通**——真实产线里，传感器是接在 PLC 上的，PLC 负责采集和判断，上位机只是"看"和"存"。
> 于是我把整条链路拆了重做。这篇记录改造过程，以及三个把我卡住的地方。

---

## 一、先说说最初的错误做法

最开始我的链路是两条**互不相干**的线：

```
真传感器(COM7) ──> Java 采集 ──> TDengine ──> 平台页面
三菱 GX 仿真器 ──> 梯形图逻辑（报警）──> 只能看，不能给数据
```

功能上都能"演示"，但有个致命问题：

- 对着传感器吹热风，**页面曲线会动，PLC 那边的报警位一动不动**；
- 因为 PLC 读不到任何真实数据，它的 `D0 > K32` 永远在拿一个手填的数在比。

这在面试里是硬伤：**你展示的是两台互不相干的东西**。

---

## 二、第一个卡点：三菱仿真器**没有对外通信口**

我一开始想"让三菱的 PLC 去读 485 传感器"，很快发现做不到：

| 方案 | 卡在哪 |
|---|---|
| GX Simulator2（FXCPU） | **仿真器只是软件模拟 CPU，没有物理通信口，也没有对外数据接口**——它可以验证梯形图逻辑，但采不了数据 |
| 真 FX3U + 485BD 板 | 要买硬件（几百到上千），而且还需要一根 USB-485 |
| CODESYS 软 PLC | **有真的 Modbus RTU 主站和 Modbus TCP 从站**，跑在 Windows 上，能用真串口 |

结论很清楚：**三菱这条线只用来证明"我会写 LD 并验证逻辑"，数据链路必须换 CODESYS。**

> 这个判断后来成了我面试里最有价值的一句话：
> **"仿真器能验证逻辑，但不能接入设备——它没有对外通信口。"**

---

## 三、改造：一条链

目标链路：

```
真传感器 (RS485/COM7)
      │  9600-8-N-1，从站 1，功能码 03
      ▼
CODESYS 软 PLC（Modbus RTU 主站）
      ├── %IW10 / %IW11  ← 湿度和温度的原始寄存器（×0.1）
      ├── rTemp = wTempRaw / 10.0          （REAL）
      ├── xAlarm := rTemp > 32.0           （BOOL）
      └── Modbus TCP 从站 :1503  ← 给上位机读
      ▼
Java 采集（读 1503）→ TDengine → 平台
```

### PLC 侧的关键动作

1. **把传感器接到 PLC 的 485 口**（我这里是 COM7），主站参数：`9600 / 8 / 无校验 / 1 停止位`、从站地址 1。
2. 通道配置：**功能码 03、起始偏移 0、长度 2**（offset0=湿度、offset1=温度）。
3. 程序里做换算和判断：

```iecst
wHumidityRaw := %IW10;
wTempRaw     := %IW11;
rHumidity    := WORD_TO_REAL(wHumidityRaw) / 10.0;
rTemp        := WORD_TO_REAL(wTempRaw) / 10.0;
xAlarm       := rTemp > 32.0;
```

4. 再把 PLC 当**从站**：`%QW0..1`（rTemp）映射到 Modbus 输入寄存器（FC04），`%QX0.0`（xAlarm）映射到离散输入（FC02），端口 1503。

### 上位机侧

点表两条就够：

```properties
device.plc-01.point.temperature.area=input
device.plc-01.point.temperature.offset=0
device.plc-01.point.temperature.type=float32
device.plc-01.point.temperature.order=CDAB

device.plc-01.point.alarm.area=discrete
device.plc-01.point.alarm.offset=0
device.plc-01.point.alarm.type=bool
```

然后 Java 就"退化"成一个搬运工 —— **不碰串口，只读 TCP**。

## 四、三个把我卡住的坑

### 坑 1：串口是独占的

CODESYS 打开 COM7 之后，Java 再打开 COM7 会直接失败。

一开始我以为是 bug，后来想明白了：**这就是真实工业约束**——现场一台设备的 485 口通常只接一个主站，不可能两边都读。

所以改造的第一件事是：**Java 必须放弃直读串口，改成读 PLC。**

### 坑 2：奇偶校验默认是 EVEN

CODESYS 的串口主站新建时，校验位默认是 `EVEN`，而传感器是 `NONE`。
表现是：**连接建立成功、但每次读都超时**，没有任何"校验错"的提示。

改一处就好：`奇偶校验 → 无`。

### 坑 3：主站/从站加反了

CODESYS 的设备树里有两个看起来很像的东西：

- `Modbus Serial Device`（这是**服务器/从站**）
- `Modbus Client, COM Port`（这才是**客户端/主站**）

我一开始加错了，怎么配都不出数。

正确的层级是：

```
Modbus_COM (Modbus COM)
 └── Modbus_Client_COM_Port   ← 主站（我们）
      └── Modbus_Server_COM_Port  ← 描述"对端那台从站"（传感器，地址 1）
```

## 五、怎么证明改造是真的

三个数字，一眼就能说明"采集与判断都在 PLC":

| 变量 | 值 | 说明 |
|---|---|---|
| `wTempIn` | **0** | 这是以前"Java 写进来"的通道，现在完全没参与 |
| `wTempRaw` | **356** | PLC 从串口读回的原始寄存器 |
| `rTemp` | **35.6** | PLC 内部算出来的温度 |
| `xAlarm` | **TRUE** | PLC 自己判断"超 32 度" |

吹热风 → `rTemp` 涨 → `xAlarm` 翻 TRUE；松手 → 回落 → 报警解除。
**从头到尾，Java 没有参与判断。**

---

## 六、软 PLC 和真 PLC 的差别（要说清楚）

我不想把这件事说过头，所以边界写在前面：

| 维度 | CODESYS Control Win（软 PLC） | 真 PLC（如 FX3U/1200） |
|---|---|---|
| 实时性 | Windows 上的软运行时，**无硬实时** | 毫秒级确定性扫描 |
| I/O | 只有**通信口**（串口/网口） | 有真实 I/O 点、隔离、断电保持 |
| 可靠性 | 会受 Windows 影响 | 工业级设计 |
| 协议 | **Modbus RTU 主站 + TCP 从站 + OPC UA，都是真的** | 同样支持 |

所以我的说法是：

> **"我的 PLC 是软的，但协议栈、寄存器映射、判断逻辑都是真的。"**
> 不吹"做过产线 PLC"，只讲"我按真实工业的分层做过一遍"。

---

## 七、这次改造最大的收获

不是"多学了一个软件"，而是**分工想清楚了**：

> **PLC 管现在，Java 管过去和远方。**
>
> PLC 负责毫秒级的采集、联锁、报警判断——它断网也照跑；
> Java 负责秒级采集、历史存储、跨网络分发、页面展示——它挂了产线不停。

这条分工线一旦立住，后面很多东西就顺了：为什么要有质量码、为什么 PLC 要再开一个 TCP 从站、为什么还要 OPC UA 服务端、为什么采集端要有退避和隔离。
