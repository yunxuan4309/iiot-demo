# PLC 与 Java 的分工（这个项目最核心的一课）

> 2026-10-24 整理。**这不是实现文档，是把"为什么工业软件要长成这样"讲清楚。**
> 面试里最能体现"你真的懂工业软件"的部分，比"我会用 MQTT"值钱得多。

---

## 〇、一句话

> **PLC 是现场的脑子：管「现在」，10ms 内必须做对。**
> **Java 是全厂的记忆：管「过去」和「远方」，存档、画图、告诉人。**

或者更短：

> **PLC 管「保护设备」，Java 管「让人知道」。**
> **电商里 Java 是老板，工业里 Java 是记录员。**

## 一、一次「超温」事件的完整时间线

假设炉子温度冲到 85℃：

| 时间 | 谁 | 做了什么 |
|---|---|---|
| **T+0 ms** | 传感器 | 测得 **85.2℃** |
| **T+10 ms** | 🔴 **PLC** | 扫到 85.2 > 80 → **`xAlarm := TRUE`** → **物理断开加热器**（继电器动作） |
| T+10 ms | 🔴 PLC | 把 `rTemp=85.2`、`xAlarm=TRUE` **留在自己的寄存器里** |
| **T+1 s** | 🔵 **Java** | 来问 PLC：「现在多少度？报警了吗？」→ 读到 `85.2` / `TRUE` |
| T+1 s | 🔵 Java | 存进 TDengine |
| **T+5 s** | 🔵 Java | 告警引擎：已持续 5 秒 → **发告警给主管**（企业微信） |
| T+1 s 起 | 🔵 Java | 每秒继续读 → 画曲线 |
| **T+60 s** | 🔴 **PLC** | 降到 74（回差 5℃）→ **`xAlarm := FALSE`** → 恢复加热 |
| T+61 s | 🔵 Java | 读到 `FALSE`，记一条「报警解除」 |
| **第二天** | 🔵 Java | 生成日报：*昨天超温 1 次，持续 60 秒，峰值 85.2℃* |

## 二、两个「永远」—— 分工的本质

| 事实 | 含义 |
|---|---|
| **PLC 那 10ms 的决策，Java 永远赶不上** | Java 1 秒才问一次。等它读到 85.2，PLC 早就把加热器断了 |
| **Java 那 1 天的报表，PLC 永远做不了** | PLC 不存历史、不联网、不会画图。它只管「现在这一刻」 |

### 两个类比

**① 医院的监护仪 vs 病历系统**

| | 监护仪 = **PLC** | 病历系统 = **Java** |
|---|---|---|
| 干什么 | 心跳异常**立刻**报警，不需要联网、不需要数据库 | 记录每分钟数值、画趋势、给医生看历史、做统计 |
| 管什么 | **现在** | **过去** |

**② 汽车 ECU vs 车联网 App**

| | ECU = **PLC** | App = **Java** |
|---|---|---|
| 干什么 | 每毫秒判断气囊弹不弹、ABS 介不介入 | 记油耗、行程、故障码，传云端给你看 |
| 关键 | **它不会问服务器「要不要弹气囊」** | 晚 1 分钟收到数据，没人在意 |

## 三、⭐ 寄存器：**扫描 ≠ 记录**

这是最容易误解的一点。

**PLC 的寄存器只存「当前值」一个数。10ms 扫描 100 次 = 覆盖 100 次，不累积。**

```
%IW0 这个 16 位寄存器
T+0ms     传感器给出 62.0  →  写入 %IW0 = 62.0
T+10ms    传感器给出 62.1  →  覆盖 %IW0 = 62.1   ← 62.0 没了
T+20ms    传感器给出 62.2  →  覆盖 %IW0 = 62.2
...
T+1000ms  传感器给出 63.0  →  覆盖 %IW0 = 63.0

⇒ 1 秒内写了 100 次，寄存器里【只留下最后一个：63.0】
```

### 能存多少个？

| 区域 | 存什么 | 典型容量 |
|---|---|---|
| `%I` / `%Q`（位） | 开关量 | 几十 ~ 几百点 |
| `%IW`（16 位字） | 模拟量输入 | 几个 ~ 几十个 |
| `%QW`（16 位字） | 模拟量输出 | 几个 ~ 几十个 |
| `%MW` / 保持寄存器 | 中间变量、设定值 | **几百 ~ 几千个字** |

> **注意：这些是「多少个不同的变量」，不是「多少个历史值」。**
> 1000 个寄存器 = 1000 个「此刻的值」，**仍然一个历史都没有**。

### 对比一下

| | **PLC 寄存器** | **TDengine（Java 侧）** |
|---|---|---|
| 存什么 | **当前值（1 个）** | **每一个历史值** |
| 新值来了 | **覆盖**旧的 | **追加**，永不覆盖 |
| 容量 | 几千个字 | GB ~ TB |
| 断电 | **丢了**（除非配保持区） | 持久化 |
| 「昨天 14:23 温度多少」 | ❌ 不能 | ✅ 能 |
| 「现在温度多少」 | ✅ **毫秒级** | ⚠️ 查库（慢） |

> **PLC 是「此刻的快照」，时序库是「整部电影」。**

## 四、⭐ 10ms 扫描 vs 1s 采集 = **丢了 99%**

```
PLC：每 10ms 看一眼
      ├─ 1 秒看了 100 次
      └─ 但寄存器里只留最后 1 次

Java：每 1s 读一次
      └─ 只拿到 100 次里的 1 次
```

**后果很严重**：假设 T+300ms 那一瞬间温度冲到 **95℃**（只持续 20ms 的一次尖峰）：

| 谁 | 看得到吗 |
|---|---|
| **PLC** | ✅ **看得到**（10ms 扫到了）→ 瞬间断开加热器 |
| **Java** | ❌ **看不到**（t=1000ms 读时已回到 63℃） |

**⇒ 这就是「保护必须放在 PLC 里」最硬的技术理由：**
**不是「Java 慢一点不好」，而是「Java 的采样率根本捕捉不到瞬态」。**

### 想记录高精度？工业界三种做法

| 做法 | 说明 | 评价 |
|---|---|---|
| **① PLC 做「窗口聚合」** | PLC 自己算每秒的 **min / max / avg**，Java 只读这 3 个值 | ⭐ **最常用**。1 秒读一次也能知道「这秒最大到过 95℃」 |
| ② 缩短采集周期 | 1s → 100ms → 10ms | 网络和存储压力 ×10 / ×100，100 台设备就崩 |
| ③ PLC 侧写 SD 卡 | 部分 PLC 支持数据记录 | 环形缓冲、MB 级、断电风险，只能事后导出 |

**⇒ ① 是正解。** 真实项目的 PLC 程序里总有一堆 `MAX()` / `MIN()` / `SUM()` 块 ——
**它们在帮上位机做预处理，让「1 秒一次」的采集也能反映真实过程。**

## 五、PLC 能「控制设备」吗？—— 能，但控制的是**执行器**

| 类别 | 例子 | PLC 能控制吗 |
|---|---|---|
| **执行器（actuator）** | 继电器、接触器、电机、变频器、电磁阀、气缸、加热器、指示灯 | ✅ **能**（这是 PLC 的输出） |
| **传感器（sensor）** | **温湿度变送器**、热电偶、压力变送器、流量计 | ❌ **不能**（它只「告诉别人」，没有「被控制」的入口） |

> **传感器只有「输出」，没有「执行」。你没法「让温度变高」—— 温度是物理世界决定的。**

### 硬件盘点（本项目）

| 已下单 | 属于 |
|---|---|
| USB-485（FT232） | 通信转换 |
| 艾克姆 RS485 温湿度变送器 | **传感器（只测量）** |
| 12V 电源 | 供电 |

**⇒ 到货后能做的是「读」，不是「控」。要「控」得另加执行器（继电器 + 灯/风扇，约 ¥15~50）。**

### 想演示「控制」，三条路

| 方案 | 需要买什么 | 花费 | 能演示什么 |
|---|---|---|---|
| **A. 纯软件** | 无 | **¥0** | PLC 内部输出 `%QX0.0` 从 FALSE→TRUE，**采集端读到这个变化**；控制逻辑是真的，物理动作是虚拟的 |
| **B. 加继电器 + 灯** | USB 继电器 或 输出板 + LED | ¥15~50 | 温度超限 → **灯真的亮** → 采集端同时看到状态变化 |
| **C. 真 PLC 硬件** | 二手 S7-1200 / 国产 PLC | ¥300~1000 | 完整工业形态，**为 demo 不值得** |

## 六、和电商的对照（这就是「工业软件 vs 电商」的答案）

| | 电商（CoolShark） | 工业（本项目） |
|---|---|---|
| 谁在「现场」 | 浏览器 / App（用户） | **PLC**（设备） |
| 谁做业务决策 | **Java 服务端**（下单、扣库存） | **PLC**（超温就断电） |
| **Java 的角色** | **决策者**（改状态） | **旁观者**（只读） |
| 失败后果 | 下单失败，重试一下 | **炉子烧了 / 人受伤** |
| 时间要求 | 几百 ms 能接受 | **10 ms 必须到** |
| Java 能不能「重试」 | 能（幂等设计） | **不能**（写不幂等 = 坑 4） |
| 数据口径 | QPS / 响应时间 | **采集完整率 / 延迟 P99 / 数据可信度** |

## 七、责任划分表（一张表背下来）

| 职责 | 🔴 PLC | 🔵 Java |
|---|---|---|
| 感知设备状态 | ✅ 每 **10ms** 扫一遍 | ⚠️ 每 **1s** 问一次（慢 100 倍） |
| **立即反应**（断开/联锁/停机） | ✅ **只有它能做** | ❌ 做不到 |
| 当前值放哪 | ✅ 自己的寄存器 | 读进内存 |
| **历史记录** | ❌ **不存**（无磁盘/无库） | ✅ **存 TDengine** |
| 画曲线 / 出报表 | ❌ | ✅ |
| 通知人（微信/短信） | ❌ 只能点灯响铃 | ✅ 告警引擎 |
| 分发给 MES / 大屏 | ❌ | ✅ MQTT |
| 操作设备（写命令） | ✅ **它的本职** | ⚠️ **能写但要克制**（坑 4） |
| **保护 / 联锁** | ✅ **永远在 PLC 里** | ❌ **绝不能放 Java**（服务器挂了保护就失效） |

## 八、面试口径（可直接背）

### 1. 分工

> 「PLC 管设备：设备出状况，它 **10 毫秒内**反应并应对（断开、停机、报警），把当前状态留在寄存器里。
> **它不存历史** —— 现场 PLC 断电重启，历史就没了。
> Java 管记录：每秒读一次 PLC 的当前值，自己存成历史，画曲线、发告警、给 MES。
> **Java 不操作设备**，最多写设定值或请求，还要读回确认（Modbus 写不幂等）。
> **保护永远在 PLC 里 —— 因为服务器会挂、网会断。**」

### 2. 为什么不能只写 Java（三个硬理由）

> 「① **GC 停顿**：JVM 回收垃圾那一瞬间应用可能停 50~200ms，这期间温度冲过 95℃ 加热器还开着；
> ② **网络断线**：Java 在服务器上，网断了它不知道炉子在烧；
> ③ **OS 调度不确定**：Windows/Linux 不是实时系统。
> 而 PLC 有确定性扫描周期、跑在设备旁边、无动态内存无 GC。」

### 3. 为什么采集端「1 秒一次」是够的（但有代价）

> 「PLC 扫 100 次，采集端 1 秒才读 1 次，**丢了 99%**。如果中间有 20ms 的尖峰，**采集端永远看不到** ——
> 所以保护必须在 PLC 里。
> 想记录得更细，做法是让 **PLC 自己做窗口聚合**（每秒算 min/max/avg），采集端只读这三个值 ——
> 这样 1 秒一次也能知道『这一秒最大到过 95℃』。」

### 4. 为什么采集端读 PLC 而不直接读传感器

> 「① PLC 已经汇总过了（8 个热电偶算最高温/平均温）；
> ② PLC 还知道设备状态（运行/停止/故障码），传感器不知道；
> ③ PLC 做过逻辑处理（滤毛刺、单位换算）；
> ④ 接线简单：读 1 台 PLC vs 读 8 个传感器 8 份点表。」

### 5. 这个项目怎么验证的

> 「我用 **CODESYS 软 PLC**（真运行时 + 内置 Modbus TCP Slave）验证了这条链路：
> PLC 里跑控制逻辑、把变量映射成寄存器、采集端当普通 Modbus 从站读。
> **换成真 PLC 硬件时，PLC 程序不用改，采集端一行代码也不用改** —— 只换一个点表文件。
> 这就是 `DeviceDriver` 抽象的价值，被一台别人写的工业级 PLC 验证了一次。」
