# 工业协议全景（面试知识面）

> 2026-10-24 整理。这份**不是 demo 的实现文档**，是把"工业软件里到底用什么协议"这件事一次说清 ——
> 面试被追问时不至于卡住，也能解释清楚本 demo 为什么选 Modbus + MQTT。

---

## 一、工业协议是分层的

越往下越「实时、封闭、和设备强绑定」，越往上越「通用、开放、和业务贴近」：

```
L4  平台 / IT 层        MQTT · Kafka · HTTP/REST · OPC UA PubSub · Sparkplug B
─────────────────────────────────────────────────────────────────────────────
L3  车间语义层          OPC UA（IEC 62541）· MTConnect
─────────────────────────────────────────────────────────────────────────────
L2  工业以太网          PROFINET · EtherNet/IP · EtherCAT · Modbus TCP · POWERLINK
─────────────────────────────────────────────────────────────────────────────
L1  现场总线            Modbus RTU(485) · PROFIBUS DP · CANopen · CC-Link · DeviceNet
─────────────────────────────────────────────────────────────────────────────
L0  仪表 / IO           4-20mA · HART · IO-Link · 干接点
```

**为什么要分层理解**：一个真实项目里**同时存在多种协议**，不是"选一个"的问题。
产线上可能同时有西门子的 PROFINET 伺服、日系的 CC-Link 机床、RS485 的电表；
到了车间层统一收敛成 **OPC UA**；再到平台层用 **MQTT** 分发。
**每一层做的是不同的转换，不是重复劳动。**

## 二、各协议的定位

| 协议 | 谁主推 | 典型场景 | 特点 / 短板 |
|---|---|---|---|
| **Modbus RTU / TCP** | 施耐德（最初）、现无主 | **仪表、变频器、电表、老旧设备** | 最简单、最普及、**无自描述**（只搬寄存器） |
| **PROFIBUS DP / PA** | 西门子 | 老产线、过程仪表 | 已被 PROFINET 逐步替代，存量仍很大 |
| **PROFINET** | **西门子** | 汽车 / 军工产线、S7-1500 | 实时（RT/IRT），**与西门子生态强绑定** |
| **EtherCAT** | 倍福（Beckhoff） | 运动控制、包装机、半导体 | ⭐ **微秒级同步**，从站芯片便宜 |
| **EtherNet/IP** | 罗克韦尔（AB） | 北美产线、重工 | 基于 CIP 协议族 |
| **CC-Link / CC-Link IE** | 三菱 | 日系设备、锂电、液晶 | 亚洲产线常见 |
| **CANopen** | 博世 | 工程机械、AGV、医疗设备 | 总线型、抗干扰强 |
| **OPC UA**（IEC 62541） | OPC 基金会 | **车间 ↔ MES**、跨厂商集成 | ⭐ **带信息模型**（不只值，还有语义）；Java 实现 = Eclipse Milo |
| **MQTT** | IBM / Eclipse | **设备上云、平台侧分发** | 轻、发布订阅、QoS、retain |
| **Sparkplug B** | Cirrus Link / Ignition | MQTT 之上的**工业规范** | 统一 topic + protobuf + birth/death 消息 |
| **Kafka** | Apache | 大数据管道、高吞吐 | **不是设备协议**，是数据总线（秒级到毫秒级，不做实时控制） |

## 三、⭐ 最关键的一课：Modbus 和 OPC UA 的本质差别

这是做本 demo 最大的收获，也是最能讲出深度的地方：

| | **Modbus** | **OPC UA** |
|---|---|---|
| 传什么 | **寄存器编号 + 16 位数据** | **变量名 + 类型 + 单位 + 量程 + 语义** |
| 自描述 | ❌ 无。`holding 0-1 = 0x4280 0x704A` 是什么？**只能查厂家手册** | ✅ 有。`ns=2;s=Machine.Temp` 明确是温度、℃、−40~120 |
| 后果 | **每个项目都要重写一份"点位表"** | 客户端可**自己发现**有哪些变量 |

**⇒ 本项目的 `points.properties`（地址 / 类型 / 字序 / 量程 / 单位），
本质上是在手工补齐 Modbus 缺失的那部分「信息模型」—— 也就是手工做了一遍 OPC UA 干的事。**

这个认知解释了为什么工业软件里"点位表 / 设备台账"是核心资产：
**协议只搬字节，语义得有人补。**

## 四、典型制造企业的现实组合

（以「重庆红宇精密工业」这类**汽车零部件 / 精密制造**企业为例；军工涉密场景另有约束）

| 层 | 大概率用什么 |
|---|---|
| 产线设备 | **PROFINET**（西门子 1500 / 840D）+ **EtherCAT**（运动轴）+ **Modbus TCP/RTU**（老设备、仪表、电表）+ 可能有 **CC-Link**（日系机床） |
| 设备 → 采集网关 | **OPC UA**（西门子 PLC 自带 OPC UA Server，是主流做法） |
| 采集 → 车间 / 集团平台 | **MQTT**（新建系统）或 **HTTP/REST**（对接 MES）/ **数据库直连**（老系统现实） |
| MES ↔ ERP | 接口 / ESB / 数据库视图 |
| ⚠️ 涉密网 ↔ 工控网 | **网闸 / 单向隔离**，**不会用公网 MQTT** |

> **军工/涉密项目里，"能不能上云"比"用什么协议"更关键。**
> 常见做法是内网自建 broker（像我们这样在 WSL 里跑 Mosquitto），数据不出网。

## 五、本 demo 的取舍（面试可直接照说）

| 选择 | 理由 | 代价 / 补偿 |
|---|---|---|
| 南向用 **Modbus** | ① **能自己造从站**（j2mod，1 小时搞定）② Java 生态最成熟 ③ 最普及，面试官一定认识 | 少了语义层 → **靠点表 + 量程校验补** |
| 没用 **OPC UA** | Eclipse Milo 学习曲线陡，还要装 Prosys 仿真服务器，**demo 时间不够** | `DeviceDriver` 接口里**已预留 `OpcUaDriver` 的位置**（计划书 §3.2） |
| 北向用 **MQTT** | 轻、发布订阅、**retain 让大屏/App 即开即有数** | 没做认证（demo 用匿名）→ 生产必须补 |
| 没上 **Sparkplug B** | 它是 MQTT 之上的规范（统一 topic + protobuf + birth/death），**属于再上一层** | 用了自定义 JSON payload，够 demo 用 |

## 六、面试口径（一句话一个）

> **分层**：「工业协议是分层的 —— 现场总线（PROFIBUS/CANopen/CC-Link）→ 工业以太网（PROFINET/EtherNet-IP/EtherCAT）→ 车间语义层（OPC UA）→ 平台层（MQTT/Kafka）。一个真实项目里是**多种协议并存**，不是选一个。」

> **EtherCAT 的位置**：「它快在**微秒级同步**，适合运动控制；但它是"控制总线"，不是"数据采集总线" —— 采集用不着它。」

> **OPC UA 的真正价值**：「不是"更快的 Modbus"，而是**自带信息模型**：它不只告诉你值是多少，还告诉你这是什么、单位是什么、量程多少。这就解决了"每个项目都要重写点位表"的问题。」

> **为什么用 MQTT 做北向**：「南向只能问（PLC 不会主动说），北向要推（几十个消费者）。**两种语义天生不同**，所以中间必须有个采集端做转换。MQTT 的 retain 还能让新订阅者立刻拿到最新值，这是 HTTP 轮询做不到的。」

> **Sparkplug B**：「MQTT 本身不规定 payload 长什么样，所以工业界在上面又加了一层规范 —— 统一 topic 命名、protobuf 序列化、还有 birth/death 消息（设备上线/离线通知）。Ignition 主推。」

## 七、延伸：如果要把本 demo 往"更真实"推进一步

| 步骤 | 做什么 | 收益 |
|---|---|---|
| 1 | 用 **Eclipse Milo** 加一个 `OpcUaDriver`，接 Prosys 仿真服务器或真西门子 PLC | 补齐 L3 语义层，`DeviceDriver` 接口不用改 → **证明"抽象层是对的"** |
| 2 | 把 MQTT payload 换成 **Sparkplug B**（protobuf + birth/death） | 从"自定义 JSON"升级到"工业规范" |
| 3 | 加 **Kafka** 做数据总线（采集 → Kafka → 时序库/告警/规则引擎） | 支撑多消费者、可回放 —— 但**demo 规模用不上，属于过度设计** |

> 📌 这三步**故意没做**：demo 的价值在"把一条链路走到底并留下证据"，
> 不在"把协议栈铺满"。**能把"为什么不做"讲清楚，比做一半更强。**
