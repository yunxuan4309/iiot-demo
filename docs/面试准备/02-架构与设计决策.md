# 02 架构与设计决策

> 一句话定位：本册回答「为什么这么设计」—— 每个决策都按「背景 → 备选 → 选了什么 → 为什么 → 代价/没做的是什么」过一遍。
> 口径：代价和「没做」必须写。面试里被追问的从来不是「你用了什么」，而是「你放弃了什么」。

---

### D1. 为什么 Java 做采集，而不是让 PLC 直连数据库？

【追问1】PLC 也能联网，为什么不让它直接写库？
【追问2】Java 挂了这个链路不就断了吗？

【简答】
**背景**：PLC 每 10ms 扫一遍，但寄存器只留「当前值」，覆盖不累积 —— 它**不存历史**；而现场要曲线、要报表、要告警、要给 MES。
**选了什么**：PLC 只做「读设备 + 判断 + 把结果留在寄存器」；Java 采集端每秒读一次，存时序库、做告警、做北向分发。

【深挖】
**备选（以及各自为什么被否）**
- **让 PLC 直连数据库**：要配连接串和数据库凭据、要自己处理断线重连和缓存，网络 IO 还可能拖住扫描任务；换库还得改 PLC 程序。
- **PLC 写 SD 卡再人工导出**：MB 级环形缓冲，只能事后导出，做不了在线监测。
- **组态软件直连（WinCC / 组态王）**：能看能存，但闭源、按点数授权、二次开发受限；我要练的是链路本身，不是一个软件怎么点。

**为什么是它**
- **时间尺度不同**：PLC 那 10ms 的决策 Java 永远赶不上；Java 那一天的历史报表 PLC 永远做不了。
- **失败隔离**：采集端崩了、库挂了，PLC 照常控制（断网也保护）；反过来，PLC 不该背数据库的可用性。
- **采集端能做 PLC 不适合做的事**：质量码、量程校验、失败退避、批量写、协议适配（Modbus / OPC UA / MQTT）、多设备并发。
- **安全边界**：数据库凭据不该出现在控制层。

**代价 / 没做的是什么**
- 多了一跳，端到端延迟到秒级 —— 对监测够用，对运动控制完全不够。
- 1s 采 10ms 的过程**丢了 99%**；要更细必须让 PLC 做窗口聚合（min/max/avg），这块我没做。
- 采集端成了单点：它挂了数据就断（所以才必须有新鲜度检查）。
- 面试话术：「PLC 管现在，Java 管过去和远方。PLC 不存历史，也不该背数据库的可用性；反过来 Java 那 1 秒一次的采样率，根本抓不到瞬态 —— 所以保护必须在 PLC 里。」

### D2. 为什么用点表配置文件，而不是把点位写死在代码里？

【追问1】一个 properties 文件能叫「架构」吗？
【追问2】配置写错了怎么办？

【简答】
**背景**：Modbus 没有语义，地址、类型、字序、缩放、量程全在厂家手册里；换一台表这些全变。
**选了什么**：纯文本点表，一个点位一行 `area/offset/type/order/scale/min/max/unit`，代码里不出现任何设备私有约定。

【深挖】
**备选（以及各自为什么被否）**
- **每设备一个驱动类**：设备一多就爆炸，改一个字序要重新编译发版。
- **放数据库 + 管理界面**：更产品化，但 demo 阶段要多一套 CRUD/权限/审计/变更记录，收益低；现场调试时改文本比开网页快。
- **硬编码常量**：最快，但等于把一台表的行为当成协议标准。

**为什么是它**
- 同一套 collector **零代码改动**读过三类设备：自写仿真从站（1502）、CODESYS 真 PLC（1503）、艾克姆真表（COM7 · 9600-8N1）。
- 字序/量程是「现场约定」，不是代码逻辑；代码只负责机制，约定放配置。
- 调试点表就是调试现场：probe 读一次 → 看哪个组合落在量程内 → 写进点表 → 跑。

**代价 / 没做的是什么**
- 配置文件本身会写错且**不报错**：offset 写成 40001 只会一直超时，order 写错只会给天文数字还标 GOOD ⇒ 必须配 probe 工具 + `min/max` 量程校验兜底。
- 没有 schema 校验、没有热加载（改完要重启）、没有版本管理/审计/管理界面；点位上千时纯文本难维护，应该上库 + 表单 + 变更记录。
- `unit` 写错不影响数值，只会让页面标错单位 —— 这种错误没人会发现。
- 面试话术：「点表是把 Modbus 缺的那部分信息模型手工补上。我换过三类设备、代码一行没改 —— 但配置写错不会报错，所以必须配 probe 和量程校验兜底。」

### D3. 为什么每设备一条虚拟线程？退避为什么是 1/2/4/8 倍、30s 封顶？

【追问1】100 条线程不算多，为什么非要用虚拟线程？
【追问2】掉线的设备一直重试不行吗？

【简答】
**背景**：100 台 × 4 点位 × 1Hz；j2mod 的 `read()` 是阻塞且 `synchronized`；一台卡死会拖垮整轮。
**选了什么**：Java 21 虚拟线程，**每设备一个任务**（`Executors.newVirtualThreadPerTaskExecutor()`），TCP 每设备独立 driver 实例，RTU 按物理链路复用一条；失败退避 **1×/2×/4×/8×，30s 封顶**。

【深挖】
**备选（以及各自为什么被否）**
- **平台线程池**：100 台要 100 条平台线程（默认栈 1MB 级），1000 台就吃紧；池化还会让一台卡死占住 worker。
- **单线程轮询**：最简单，但一台超时 2s，后面 99 台全等。
- **Netty / 异步 Modbus**：性能最好，但 j2mod 是阻塞 API，换异步等于重写协议栈，demo 不划算。

**为什么是它**
- 虚拟线程的阻塞 IO 不占平台线程，100 条几乎零成本；写法还是同步直线代码，不用回调。
- **隔离才是目的**：线程 + 连接 + 读超时（默认 2000ms）+ `catch (Throwable)` 四层；实测 unit=5 卡死时，其余 9 台仍 1.2~2.6ms。
- 退避是「别给掉线设备继续添乱」：实测退避后 STALE 每轮只 +80（20 台×4 点），说明轮询频率真降了。
- 断线演练（跑着的时候杀掉从站）：完整率从 100% **平滑降到 61.5%**，STALE 400 / BAD 0，采集器不崩、跑完退出码 0。
- 100 台压测：24000 点、完整率 **100%**、388 点/秒、P50 1.27ms / P95 4.14ms / P99 9.95ms、写入失败 0、队列丢弃 0。

**代价 / 没做的是什么**
- 虚拟线程不解决 `synchronized` 串行：共用 driver 实例会让 100 台退化成串行 —— 所以必须每设备一个实例（这是实测踩出来的）。
- 没有动态设备管理（增删要重启）、没有按设备优先级调度、没有熔断/半开（只有退避）。
- 观测只有失败轮次/延迟分位/质量码占比，没有 per-device dashboard、没有告警联动。
- 线程数 = 设备数，上万台要分片/多进程，这套模型不直接扩展。
- 面试话术：「我不是为了炫虚拟线程 —— 100 台阻塞 IO，用虚拟线程写法还是同步的，但成本几乎为零。真正值钱的是隔离：一台卡死，其余 9 台还是 1~2ms。」

### D4. 为什么选 TDengine？为什么是超级表 + 每设备每点位子表？

【追问1】MySQL 不行吗？
【追问2】为什么用 REST 而不是 JDBC？

【简答】
**背景**：400 点/秒持续写入，查询是「按时间范围 + 按设备/点位」。
**选了什么**：TDengine 3.3（WSL2 免 root），超级表 `telemetry(ts, val, quality) TAGS(device, point, unit)`，**每个「设备×点位」一张子表**（`d_<device>_<point>`，首次写入自动建，100×4=400 张）；写入走 **REST 6041**（原生 6030 要 native 库，Java 用不上），攒 **500 点或 500ms** 发一批。

【深挖】
**备选（以及各自为什么被否）**
- **MySQL**：写入/存储/按时间聚合都吃亏；400 点/秒一天约 3400 万行，索引和清理都疼。
- **InfluxDB**：也合适，但当时选型偏向 TDengine（工业圈常见、SQL 风格、国产）。
- **QuestDB / ClickHouse**：接口已经抽了 `TelemetryRepository`，换库只改一个实现类（`CountingTelemetryRepository` 就是为对比留的）。
- **TDengine JDBC（native）**：Windows 上没有 `libtaos.so`，还要跨 WSL；REST 就是一个 HTTP POST，零依赖。

**为什么是它**
- 超级表 + 子表天然贴合「设备 × 点位」：schema 统一、子表自动建、`last() + partition by device, point` 直接出最新值（`/api/latest` 就这么查的）。
- 批量把 HTTP 开销摊掉：每批约 123 点、195 批写 24000 点，HTTP ≈ 3 次/秒，而不是 100 次/秒。
- 实测 388 点/秒、写入失败 0、队列丢弃 0。

**代价 / 没做的是什么**
- 子表数 = 设备 × 点位，设备/点位多了元数据会膨胀，要规划库和分表策略。
- 没有保留策略（KEEP）、没有降采样/连续查询、没有乱序/迟到数据处理 —— 数据会一直长。
- 拼 SQL 字符串有转义风险：库名/表名做了 `sanitize`、TAG 值做了 `escape`，但**不是参数化**；生产应该用官方连接器或 PreparedStatement。
- 队列满时**丢点并计数**（`droppedPoints`），不阻塞采集 —— 有意的取舍，但意味着「库慢」会静默丢数据，只能靠计数发现。
- 单机无副本、跑在 WSL2 里；Windows 侧只监听 `[::1]`，Java 必须加 `-Djava.net.preferIPv6Addresses=true` 且用 `localhost` 而不是 `127.0.0.1`（踩过）。
- 面试话术：「时序数据是持续产生、按时间查，关系库不适合。超级表给 schema、子表给每设备每点位，写入攒 500 点或 500ms 走 REST —— 388 点/秒、0 失败。没做的是保留策略和降采样。」

### D5. 为什么平台是只读 API + ECharts，而不是让前端直接查库？

【追问1】直接给前端一个 TDengine 连接不是更简单？
【追问2】你说的「查询层语义」到底是什么？

【简答】
**背景**：页面要设备列表、当前值、曲线；数据在 TDengine 里。
**选了什么**：Spring Boot 3.2.5 **只读三个接口**（`:8080` 的 `/api/overview`、`/api/latest`、`/api/series`），后端用 JDK HttpClient 打 TDengine REST，前端 ECharts **本地副本**。

【深挖】
**备选（以及各自为什么被否）**
- **前端直连 TDengine REST**：浏览器要拿到库地址和 root 凭据，CORS 和网络暴露，SQL 直接暴露给前端。
- **后端 JDBC 直查**：Windows 侧没有 native 库；Spring Data 对 TDengine 方言支持不好，最后还是要手写 SQL。
- **Grafana**：开箱即用，但页面就不是「我做的」，也讲不出业务语义（质量码、过期、设备分组）。

**为什么是它**
- 凭据和 SQL 留在后端，浏览器只拿 JSON。
- 有些语义**只能在查询层算**：`ageSeconds`/`stale` 必须拿「现在」减最新点时间；直接查库拿到的是「写入那一刻的 GOOD」，采集端挂了它也是 GOOD。
- 跨 WSL 用 REST 最省事，零 native 依赖，以后还能走 SSH 隧道连远端。
- ECharts 本地副本，离线可跑，不依赖 CDN。

**代价 / 没做的是什么**
- 多一跳，没有缓存/分页/限流/鉴权；`/api/series` 直接把原始点给前端（10 分钟 24 万行），**没做聚合下推/降采样**，数据量再大前端会卡。
- 后端没有连接池/重试策略，TDengine 挂了给 503（有可读错误，但没有降级）。
- 前端是原生 JS + ECharts，没组件化/状态管理，页面一复杂就难维护。
- 只读：没有任何写接口（不写设定值、不下发命令）—— 这是有意的安全边界，但也意味着「控制」这块没做。
- 面试话术：「浏览器的凭据和 SQL 都不该出后端；更重要的是新鲜度只能在查询层算 —— 库里最后一条永远是 GOOD，直接查库看不出来采集端已经死了。」

### D6. 为什么 PLC 侧要同时做 RTU 主站和 TCP 从站？

【追问1】让 Java 直接读传感器不是少一跳吗？
【追问2】一个串口为什么不能两边都读？

【简答】
**背景**：真表只有 RS485/Modbus RTU；上位机（Java）只会 Modbus TCP。
**选了什么**：CODESYS 里同时开两个角色 —— 串口 **Modbus RTU 主站**（COM7 · 9600-8N1 · 从站 1 · FC03 · 起始 0 · 长度 2 · 周期 100ms）读传感器；以太网 **Modbus TCP 从站 :1503** 给 Java 读。

【深挖】
**备选（以及各自为什么被否）**
- **Java 直接读传感器**（我早期就这么干，`points-sensor.properties` + `RtuModbusDriver`）：能跑，但采集方向和真实产线相反，而且 COM 口独占 —— PLC 一在线，Java 就打不开同一个口。
- **只做 TCP 从站、数据靠 Java 写进去**（BridgeMain 写 `%IW0` 代采）：判断虽然在 PLC，但数据来源是 Java，断网就没了。
- **买带 485 的真 PLC**（FX5U 自带 485 + 以太网）：最标准，但要花钱，本机也装不了大型 PLC 软件。

**为什么是它**
- 真实产线形态就是「设备先接 PLC，PLC 采集与判断，上位机读 PLC」。
- 串口独占 + 485 半双工，天然只能有一个主站；让 PLC 当主站，Java 退到「只读」，职责干净。
- 断网也保护：判断在 PLC，链路断了不影响超温断电。

**代价 / 没做的是什么**
- 串口主站必须配超时和「自动重启通信」：不勾，对端重启后主站停在错误态，通道「错误处理=保持最后值」会把值**冻结** —— 界面上还有数，实际早不刷新了。
- 软 PLC 没有硬实时/电气隔离/断电保持；COM7 被 PLC 占着时，Java 不能再直接读表。
- 只读 2 个寄存器（湿度/温度），没做写（设定值/命令），也没做多从站轮询。
- 早期「Java 代采」那版还在仓库里（BridgeMain + points-codesys-writable），讲的时候要主动说清演进，别让人以为现在是反的。
- 面试话术：「真实产线是 PLC 读设备、上位机读 PLC。串口是独占的、485 是半双工的，只能有一个主站 —— 所以让 PLC 当主站，Java 退到只读，判断也就落在了 PLC 里。」

### D7. 已经有 Modbus 了，为什么还要再开一个 OPC UA 服务端？

【追问1】OPC UA 是要替代 Modbus 吗？
【追问2】匿名不危险吗？

【简答】
**背景**：Modbus 没有语义，跨系统对接时对方要「自己发现有哪些变量」。
**选了什么**：CODESYS 自带 OPC UA 服务端（4840），5 个变量勾进符号配置并下载，客户端可匿名 Browse / Read。

【深挖】
**备选（以及各自为什么被否）**
- **只留 Modbus**：够用，但每个消费者都要一份点表 + 手册，接一个系统配一遍。
- **Java 侧自己做 OPC UA 服务端（Eclipse Milo）**：能把库里的值也暴露成信息模型，但要写地址空间、证书、会话，工作量大，且和 PLC 真实变量脱节。
- **什么都不做**：JD 点名 OPC UA，零证据最吃亏。

**为什么是它**
- **不是替代关系**：南向设备通信还是 Modbus（存量设备只有它、简单、开销小），北向跨系统用 OPC UA（自描述）。同一份数据两条路都能读，看对方说什么协议。
- 成本几乎为零：CODESYS 运行时自带，勾变量 + 下载即可。
- 能证明「懂信息模型」：客户端 Browse 出 `DeviceSet → PLC → Application → PLC_PRG → rTemp`，不靠点表。

**代价 / 没做的是什么**
- **匿名 + SecurityPolicy None**，只用于演示；生产必须关匿名、Basic256Sha256 + 客户端证书 + 符号权限。明文密码在 None 通道会被规范拒绝。
- 只做了 Browse + Read，**没做 Subscription（数据变更通知）/ Method 调用 / 历史访问**。
- 只暴露 5 个变量；符号配置改完**不下载不生效**（踩过：勾了、编译了，服务端里什么都没有）。
- 客户端是 Python asyncua 探针，不是生产客户端；Java 侧没接 OPC UA（Eclipse Milo 只在计划里）。
- 面试话术：「两个不是替代关系：南向 Modbus 采设备，北向 OPC UA 给系统集成。CODESYS 自带服务端，我勾了 5 个变量下载，客户端匿名 Browse 就能读到 rTemp=22.5 —— 但匿名只是演示，生产必须关。」

### D8. 为什么北向用 MQTT QoS1 + retain？

【追问1】为什么不是 QoS2？
【追问2】retain 会不会让人误以为是实时值？

【简答】
**背景**：数据要分发给大屏/App/MES，消费者数量不定，新消费者上线要立刻有数。
**选了什么**：Mosquitto（WSL2，1883），topic `iiot/{device}/{point}`，QoS **1**，`retain=true`，payload 带质量码和时间戳。

【深挖】
**备选（以及各自为什么被否）**
- **HTTP 轮询**：N 个消费者 = N 组轮询，压力 ×N；新消费者要等下一个周期。
- **QoS0**：最轻但会丢；工业数据丢一条可能漏一次越限。
- **QoS2**：恰好一次，四次握手，1Hz 采集没必要。
- **Kafka**：吞吐高但重、要运维，demo 规模用不上（它是数据总线，不是设备协议）。

**为什么是它**
- 发布订阅解耦：一次发布，broker 分发给 N 个消费者，采集端不知道谁在消费。
- QoS1「至少一次」：宁可重复不可丢；重复可以靠 payload 里的 `ts` 去重（**我们没做去重**，消费端要自己做）。
- retain 解决「新订阅者上线没数」：实测发布端停掉后，`mosquitto_sub -C 1` 立刻拿到最后一条。
- 北向失败不影响南向：`publish()` 内部 catch 只计数。

**代价 / 没做的是什么**
- 匿名（`allow_anonymous true`），无 TLS/ACL；单 broker 无集群，没配持久化，重启丢 retain。
- 没有 outbox/重试：发布失败只计数，消息就没了 ——「至少一次」只保证 broker 收到之后的语义，不保证我发出去。
- 没有 Sparkplug B（没有 birth/death、没有统一 payload schema），消费者要自己解析 JSON。
- 重复消息没去重，retain 只有最后一条（不是历史）。
- 面试话术：「QoS1 是宁可重复不可丢，1Hz 采集用不上 QoS2 的四次握手。retain 让大屏一上线就有数 —— 我实测过，发布端停掉，新订阅者照样立刻拿到最后一条。代价是重复消息要去重，我没做。」

### D9. 为什么三菱 GX Works2 只用来验证 LD 逻辑，不承担数据链路？

【追问1】三菱不是 JD 点名的吗，怎么不拿它采数据？
【追问2】那你的 LD 到底证明了什么？

【简答】
**背景**：JD 点名「精通至少一种主流 PLC 软件 + LD/ST/FBD」；本机是 Win11 家庭版，TIA Portal / Studio 5000 装不了；三菱 GX Works2 能装、有 GX Simulator2。
**选了什么**：GX Works2 写 LD（`LD M8000` → `CMP D0 K32 M0` → `M0` 驱动 `Y0`），用 GX Simulator2 验证逻辑（D0=40 时 Y0 导通、D0=20 断开）；**数据链路完全不放在三菱侧**，走 CODESYS。

【深挖】
**备选（以及各自为什么被否）**
- **用三菱仿真器采数据**：**做不到** —— 仿真器的 X/Y/D 只是内存里的位和字，没有物理通信口，也不跑 Modbus 协议栈；对外只有 MX Component 这类私有通道。
- **买二手 FX3U**：编程口是 **RS-422**（只给编程软件），要加 485 板 + 以太网模块才等价于 FX5U，落地 ¥400~700，为 demo 不值。
- **只讲不练**：JD 要「精通」，零证据最吃亏。

**为什么是它**
- 语言和扫描概念可迁移：触点/线圈/比较、`M8000` 常 ON、扫描周期，这些在西门子/罗克韦尔/CODESYS 上是同一套 IEC 61131-3 思路。
- 三菱侧的价值是「证明我摸过另一家的工具链」，不是「证明我能接三菱的上位机」。
- **仿真器模拟的是 CPU 和内存，不是设备** —— 让它验证逻辑，让真运行时（CODESYS）验证链路，两件事分开做才说得清。

**代价 / 没做的是什么**
- 三菱侧**零数据链路、零真实硬件**：没写过 MC 协议 / MX Component，没接过 FX5U。
- LD 只有 11 步、一个比较；三菱侧没写 ST/FBD，不能证明「三菱的 ST 我也会」。
- 面板上 100ms 是 GX Simulator2 的仿真节拍，不是真机指标，不能当性能数据。
- 三语言同跑（LD/ST/FBD）是在 **CODESYS** 上做的，三菱只是补充证据。
- 面试话术：「GX Simulator2 是 CPU 仿真器，没有物理口也不跑协议栈，采不到数据 —— 它只能验证逻辑。数据链路我放在 CODESYS 的真运行时上，三菱这边证明的是我摸过另一家的工具链和 LD。」

### D10. 哪些是明确没做的？

【追问1】这套东西能上线吗？
【追问2】没做的部分，生产该怎么补？

【简答】
**背景**：demo 的目标是「把工业现场的坑做成工程约束」，不是做产品；所以边界要主动划，而不是等人问。
**选了什么**：明确列五条「没做」，每条都给「生产该怎么补」。

【深挖】
- **无认证**：平台三个接口裸奔，没有登录/权限；MQTT 匿名；OPC UA 匿名 ⇒ 生产：关匿名、TLS、ACL、账号/角色权限、按角色分视图和操作权限。
- **无高可用**：TDengine 单机（WSL2）、Mosquitto 单 broker、collector 单进程、platform 单实例，没有副本/主备/健康检查/自动重启 ⇒ 生产：多副本或集群、采集端多实例按设备分片、守护进程或 K8s。
- **无安全联锁**：`xAlarm` 只是置一个 BOOL，没有真正切断输出/停机回路；软 PLC 无电气隔离、无看门狗、无 SIL/PL ⇒ 生产：安全功能必须走安全 PLC + 硬接线回路，不能靠软 PLC。
- **无断电保持**：CODESYS Control Win 跑在 Windows 上，断电/重启后变量回初值；没配 RETAIN/PERSISTENT，也没配 UPS ⇒ 生产：保持区 + UPS + 断恢复策略。
- **只有 4 个点位**（温度/运行时长/电机运行/报警）：够验证链路，不够覆盖真实产线 —— 一台设备几十到几百点，还有批次/工单/配方。
- **另外没做**：Profinet/EtherNet-IP 零实操、MES/EAM 集成、降采样/保留策略、乱序/迟到数据、写操作的重试安全（写不幂等只记录未制造）、审计日志。
- **为什么敢留**：每条「没做」都能说清「生产该怎么做」，比假装做了强；面试官问「能上线吗」，正确答案是「不能，差这几块」。
- 面试话术：「这不是生产系统：单机、无认证、无高可用、无联锁、4 个点位。但我能说清每一块生产该怎么补 —— 认证走 OIDC + TLS，高可用走多副本 + 设备分片，联锁必须回到安全 PLC 和硬回路。边界清楚比功能多更可信。」
