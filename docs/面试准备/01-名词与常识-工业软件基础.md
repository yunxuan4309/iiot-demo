# 01 名词与常识 · 工业软件基础

> 一句话定位：本册解决「面试官说的词我听不懂 / 我说的话他听不懂」。
> 口径：每个 Q 按「是什么 → 和什么容易混 → 我们项目里怎么用的」三段讲；数字全部来自本项目实测，不编。

### Q1. PLC 是什么？扫描周期为什么是毫秒级？

【追问1】PLC 10ms 扫一次，你 1 秒才采一次，中间的值去哪了？
【追问2】既然 Java 也能算，为什么判断不能放在 Java 里？

【简答】
PLC 是跑在设备旁边的控制计算机，循环执行「读输入 → 跑程序 → 写输出」，一圈叫扫描周期，典型 1~20ms（我们这台 CODESYS 的任务周期 10ms）。
它管「现在」：超温就断输出，断网也照做。Java 1 秒读一次，管的是「过去和远方」。

【深挖】
- **是什么**：PLC = 可编程逻辑控制器，语言按 IEC 61131-3 分 LD/ST/FBD/IL/SFC；我们这台 CODESYS 用 **LD/ST/FBD 三种语言写了同一段逻辑**并在线跑通，`xAlarm := rTemp > 32.0` 就在 `PLC_PRG` 里。
- **为什么是毫秒级**：它的输出直接驱动继电器/阀/电机，必须在一圈内完成「读—算—写」；跑在设备旁、无 GC、无 OS 调度抖动，所以周期是**确定性**的。三菱 GX Simulator2 面板显示的 100ms 是仿真器节拍，不是真机指标。
- **和 Java 秒级采集的区别**：PLC 10ms 扫 100 次/秒，但寄存器**只留最后一个值**（覆盖、不累积）；Java 1 秒读 1 次 ⇒ 只拿到 100 次里的 1 次，**丢了 99%**。一次只持续 20ms 的 95℃ 尖峰，PLC 看得到并立刻断开，Java 永远看不到。
- **项目里**：吹风机加热真表实测 31.4℃(FALSE) → **34.2℃(TRUE)** → 峰值 41.4℃ → 31.5℃(FALSE)，**Java 全程没做判断**；这也是「判断在 PLC、记录在 Java」这条分工的硬证据。
- **所以**：想记录得更细，正确做法是让 PLC 做**窗口聚合**（每秒算 min/max/avg），而不是把采集从 1s 缩到 10ms —— 后者网络和存储要 ×100。
- 面试话术：「PLC 管现在，Java 管过去和远方。10ms 和 1s 差的不是速度，是**采样率根本抓不到瞬态** —— 所以保护必须在 PLC 里，因为服务器会挂、网会断。」

### Q2. Modbus RTU 和 Modbus TCP 到底差在哪？

【追问1】PDU 一样，那到底什么是「外壳」？
【追问2】为什么你的端口不是 502？

【简答】
两者 PDU 完全相同（功能码 + 数据），只是外壳不同：RTU 走 RS485 串行口，地址 1 字节 + PDU + **CRC16 两字节**；TCP 走以太网，**MBAP 头 7 字节**（事务号 2 + 协议号 2 + 长度 2 + 单元号 1）+ PDU，没有 CRC。

【深挖】
- **是什么**：RTU 是二进制紧凑帧，一问一答、串行、**没有事务号**，单帧上限 256 字节；TCP 多 7 字节 MBAP 头，靠 TCP 做校验，端口 502。
- **容易混**：以为「TCP 就是 RTU 换根网线」—— PDU 一样，但寻址、校验、并发都不同；TCP 的**事务号**是为了在一条连接上并发多请求时配对（抓包里请求应答都是 `00 2f`），RTU 串行一问一答所以不需要。
- **容易混（二）**：TCP 的**单元号**在直连时没意义，只有经过 485 网关时才用来区分后面挂的哪台从站 —— 这也是「一个 TCP 连接可以读写多个 unitId」的原因。
- **项目里**：两种我都自己写了主站（`TcpModbusDriver` / `RtuModbusDriver` 共用 `AbstractModbusDriver`），点表、质量码、字序一套代码。真表 RTU：COM7 · 9600-8N1 · 从站 1，单轮 29~43ms（首轮 128ms）；TCP 读 CODESYS 从站 `:1503`。
- **为什么不是 502**：502 是特权端口，要管理员权限；我们用 1502（仿真）/1503（CODESYS）。代价是 Wireshark 默认只把 502 当 Modbus —— 抓 1502 时过滤出来 **0 帧、全是 data**，得加 `-d tcp.port==1502,mbtcp`（解码器名是 `mbtcp`，写 `modbus` 会报参数非法）。
- **抓包证据**：85 个包里有 43 个 Modbus，循环是 `FC01 → FC02 → FC03` —— 因为 4 个点位分属线圈 / 离散输入 / 保持寄存器。
- 面试话术：「PDU 一样，壳不一样：RTU 是地址+CRC 走 485，TCP 是 7 字节 MBAP 头走以太网。TCP 多事务号是因为它能并发，RTU 一问一答不需要。」

### Q3. 主站/从站是什么？单元号/从站地址又是干什么的？

【追问1】TCP 上你是客户端，怎么又是主站？
【追问2】一个端口下面能挂几台设备？

【简答】
Modbus 是**主从**协议：**只有主站发起请求**，从站只能被动应答，从站之间不能互相说话。单元号/从站地址就是「这根总线上问的是哪一台」（RTU 1~247，0 是广播）。

【深挖】
- **是什么**：今天更常叫 client/server，但语义没变 —— 发起方永远是主站。请求里带地址/单元号，只有对应那台才回。
- **容易混**：①「主站」不等于「服务器」—— TCP 上 Java 是 **client**，但在 Modbus 语义里它是**主站**（发起方）；② `host:port` 和 `unitId` 是两个维度，一个 TCP 连接可以服务多个 unitId。
- **项目里**：真表从站地址 1；压测 100 台仿真从站共用 `127.0.0.1:1502`，靠 **unitId 1..100** 区分（`--fanout 100` 就是把模板复制 100 份、只改 unitId）。
- **从站是自己造的**：仿真从站和 probe 工具都用 j2mod（主站、从站同一个库），所以能造 `--hang-unit`（收到请求但故意不回）这种现场不好复现的故障。
- **故障注入**：`--hang-unit 2` 能让 unit=2 单独「收到请求但不回包」，其余照常 —— 这是「一台设备拖不垮全场」的最小验证，也是现场最难查的那种故障（ping 得通、端口也通，就是不回数据）。
- **为什么按物理链路复用连接**：RS485 是**半双工**，一条总线同一时刻只能有一个请求；一个 COM 口也只能被打开一次。所以 `DriverRegistry` 按「物理链路」复用驱动，而不是每台设备 new 一个 —— 否则第二台 RTU 设备直接报错。
- 面试话术：「Modbus 里只有主站能开口，从站一辈子被动。所以采集端必然是主站；PLC 也一样 —— 它当我的从站（1503），同时自己当主站去读传感器（COM7）。」

### Q4. FC01/02/03/04/05/06 各是什么？为什么一轮要发好几种？

【追问1】FC03 和 FC04 有什么区别？
【追问2】从站回异常码你怎么看？

【简答】
功能码决定「读/写哪个区」：01 读线圈、02 读离散输入、03 读保持寄存器、04 读输入寄存器、05 写单线圈、06 写单寄存器。四个区是四张表，不能混着读。

【深挖】

| 功能码 | 读/写什么 | 地址区 | 我们哪里用到 |
|---|---|---|---|
| FC01 | 读线圈（可读写位） | 0xxxx | `motor_running` |
| FC02 | 读离散输入（只读位） | 1xxxx | `alarm`（PLC 的 `xAlarm`） |
| FC03 | 读保持寄存器（可读写 16 位） | 4xxxx | 温度 / 运行时长 / 真表温湿度 |
| FC04 | 读输入寄存器（只读 16 位） | 3xxxx | 真表不支持，试过回异常码 `01` |
| FC05 | 写单个线圈 | 0xxxx | 写 `motor_running`，写完读回确认 |
| FC06 | 写单个保持寄存器 | 4xxxx | 早期 BridgeMain 写 `%IW0`（`temp_in`） |

- **容易混**：FC03 与 FC04 都是「读 16 位寄存器」，差别是**保持寄存器可写、输入寄存器只读**；写要用 05/06，不能用 03。异常码也要会看：`01` = 非法功能（设备没实现这个功能码），`02` = 非法数据地址（地址越界）。
- **项目里**：4 个点位分属三个区，所以一轮采集要发 3 种功能码（抓包就是这样 `FC01 → FC02 → FC03`）；真表只实现了 FC03，我试 FC04 直接被回 `01`。
- **写必须读回确认**：FC05 写完 `ACK=true`、再读回 `motor_running=true` 才算成功 —— Modbus 写不幂等，超时重发可能让执行机构动作两次，所以「写成功」不能只看有没有报错。
- 面试话术：「四个区对应六个功能码，读保持寄存器是 03、读输入寄存器是 04，写是 05/06。现场设备经常只实现一部分 —— 真表就只认 03，04 直接回异常码 01。」

### Q5. 寄存器只有 16 位，那 32 位的值怎么读？

【追问1】两个寄存器读回来，怎么知道是 float 还是 int？
【追问2】为什么点表里有的点位没有 order？

【简答】
Modbus 寄存器**固定 16 位**（0~65535），Float32/Int32/UInt32 要占**两个连续寄存器**。协议只保证「每寄存器 2 字节、字节内高字节先传」，怎么拼是厂家约定 —— 类型、字序、缩放三样都得从点表来。

【深挖】
- **是什么**：16 位 = 2 字节，32 位 = 4 字节 = 两个寄存器。读的时候一次读 2 个（`FC03` 起始 0、数量 2），回来 4 个字节。
- **容易混**：①「读了 2 个寄存器」≠「得到一个 float」，还要知道类型（float32 / int32 / uint32）、字序、缩放；② **字节序**（一个寄存器内两个字节）Modbus 规定了大端，**字序**（两个寄存器谁在前）协议完全没规定 —— 混在一起就会误以为「Modbus 字节序乱」。
- **项目里**：`temperature` 是 float32 占 2 个寄存器（CODESYS 的 `REAL`）；`runtime_hours` 是 uint32 占 2 个；真表的温度/湿度是 **int16 / uint16 + scale 0.1**，只占 1 个 —— **16 位天生没有字序**，所以点表里这两个点位不填 `order`（填了反而是错的）。
- **缩放为什么也要配置**：真表 `offset1` 读回 356 表示 35.6℃，除以 10 才是工程值；温度用 int16 才能表示负温，湿度用 uint16 就够。这个 0.1 来自手册，不是协议。
- **量程是最后一道防线**：类型/字序/缩放任何一个配错，程序都不报错，只会把错值一路标成 GOOD 送到页面。所以点表还有 `min`/`max`，超范围判 BAD。
- 面试话术：「Modbus 只规定寄存器 16 位。32 位值跨两个寄存器，类型、字序、缩放全靠点表约定 —— 这三样缺一个，读出来的数就不能用。」

### Q6. 字序 ABCD/CDAB/BADC/DCBA 是什么？为什么会有四种？

【追问1】配错了会怎样？
【追问2】怎么验证字序才对？

【简答】
32 位值拆成高低两个 16 位字时，「哪个字在前」有四种约定：ABCD（正序）、CDAB（两字互换）、BADC（字内字节互换）、DCBA（全反）。协议不管这件事，所以只能按点位配置、按实测确认。

【深挖】
- **为什么会有四种**：不同 CPU 大小端、不同厂家实现习惯不同。**国内仪表常见 CDAB**（低字在前）；我实测 CODESYS 的 `REAL` 是 **CDAB**，RTU 测试桩是 **ABCD**。
- **容易混（一）**：以为一台设备只有一种字序 —— 抓包这一帧里，`reg0/reg1` 按 **CDAB** 是温度（62.2℃），`reg2/reg3` 按 **ABCD** 是运行时长（1234h），**同一帧两种字序**。
- **容易混（二）**：以为配错会报错 —— 不会，程序照样标 GOOD；以为配错一定很大 —— 按 ABCD 解温度得到 `-7.36e18`（天文数字），但另一帧里得到 `1.88e-31 ≈ 0`。**不能只靠「看着不对」发现**，必须量程校验。
- **项目里**：`points.properties` 每个点位单独 `order=`；把 order 从 CDAB 改成 ABCD，同一个值解出 `-15222668117814542000.00℃` —— 证明配置真的在驱动解码，不是摆设；换一台表只改这一行，代码不动。
- **验字序的坑**：必须用**低 16 位非零**的值。`90.0 = 0x42B40000`，低 16 位是 `0x0000`，于是「offset 0 + CDAB」和「offset 1 + ABCD」能解出同一个 90.0 —— **起点错一位、字序换一种，互相抵消了**；`25.5 = 0x41CC0000` 同理。换成 `90.1`（`0x42B43333`）或 `25.6`（`0x41CCCCCD`）才唯一。
- 面试话术：「字序不是猜的，是实测的。同一帧里前两个字按 CDAB 是 62.2℃，后两个字按 ABCD 是 1234 小时 —— 所以字序必须按点位配，而且要用低 16 位非零的值去验，整数和小数点后 .5 都验不出来。」

### Q7. 40001 和 offset 0 到底差在哪？

【追问1】填错了会读到隔壁的值吗？
【追问2】现场怎么快速判断是 1 基/0 基搞混了？

【简答】
`40001` 是**惯用编号**（1 基，给人看的，4 表示保持寄存器区）；报文里传的是 **0 基偏移**：`40001 ↔ offset 0`、`40002 ↔ 1`。手册、组态软件、HMI 上写的通常是惯用编号。

【深挖】
- **容易混**：以为「填 40001 也能读到，只是错一位」。实际是**地址越界** → 从站不响应 → 客户端重试 → **永远超时**，不是读到错值。
- **项目里**：我把点表 `temperature.offset` 改成 `40001`，报文里出现 `9C 41`（= 0x9C41 = 40001），而仿真从站寄存器只到 offset 3，于是**不回包** → j2mod 重试 5 次 → `Socket timeout` → 判 BAD；改回 `0` 立刻正常读出 4 个点。
- **现象形态很关键**：不是「读到了错误的值」，而是「一直超时」。现场调一台表，地址「看起来是对的」却怎么都不回，就要怀疑 1 基/0 基。
- **落地约定**：点表里 `offset` 一律写 0 基，注释里写清对应的惯用编号（`reg[0] (40001)`），probe 工具打印时两种编号并列，避免下次再混。
- 面试话术：「40001 是给人看的编号，报文里是 0 基的 0。混了不是读错值，是永远超时 —— 因为从站那边地址根本不存在，它不会回你一个错值。」

### Q8. RS485 和 9600-8-N-1 分别是什么意思？A/B、终端电阻、共地呢？

【追问1】A/B 接反会烧设备吗？
【追问2】现场读不到，你先查什么？

【简答】
RS485 是**差分**串行总线（A/B 两根线），半双工、多点、抗干扰、距离远。`9600-8-N-1` = 波特率 9600、8 数据位、**N 无校验**、1 停止位 —— 两边**四个参数必须完全一致**，错一个就乱码或超时。

【深挖】
- **容易混**：① A/B 不是电源正负，**接反不烧**，只是完全读不到；② 终端电阻不是每个节点都装，是总线**两端**各 120Ω（台面短距离 demo 我们没装）；③ 「共地」不是随便接一根 —— 电源负 + USB-485 的 GND 都要接，否则差分信号没有共同参考。
- **项目里**：艾克姆 IKM10000WS01 · **COM7** · **9600-8N1** · 从站 1 · **FC03** · `offset0=湿度 / offset1=温度`（均 ×0.1），单轮 29~43ms；USB-485 是 FT232R，**没有 VCC**（不能给传感器供电），端子 `T/R+ T/R- RXD+ RXD- GND`。
- **没有硬件时怎么验**：用 com0com 造一对虚拟串口（COM5 ↔ COM6），一头跑 `RtuSlaveMain` 当从站、另一头给主站打开 —— 协议链路先在没有硬件的情况下跑通，真表到了只换串口号。
- **踩过的**：A/B 接反（完全读不到）、没共地（通电后指示灯不亮、读不到）、寄存器顺序猜反（以为 offset0 是温度，实际是湿度，读出来 64.6「℃」其实是湿度）。
- **排障顺序（我栽过）**：物理（接线/供电/共地）→ 电平（A/B 有没有反）→ 参数（波特率/校验/从站号）→ 数据（地址/类型/字序）。我有一次 **A/B 根线还没接**就扫了 16 组参数组合，全白扫 —— 排障不是「试更多可能性」，是「按依赖顺序逐层确认」。
- **串口是独占资源**：CODESYS 在线占着 COM 口时，Java 再打开同一个口直接失败。所以「PLC 读」和「上位机读」在物理层就是二选一，现场才需要网关或多串口卡。
- 面试话术：「485 排障我按物理→电平→参数→数据四层走。A/B 接反不烧，只是读不到；参数错一位就全乱。这些不是书本知识，是我扫了 16 组参数才发现根线没接换来的。」

### Q9. 质量码 GOOD/STALE/BAD 是什么？断线为什么不能补 0？

【追问1】STALE 和 BAD 差在哪？
【追问2】补 0 到底危险在哪？

【简答】
每个采样点除了值还带质量码：**GOOD** = 本轮真读到了；**STALE** = 本轮读失败、保留上次好值并标明「这是旧的」；**BAD** = 从来没读到过好值（值为空，不补 0）。

【深挖】
- **为什么不能补 0**：0℃ 会被下游当成真值 —— 误报警、误联锁、操作工白跑现场，**比没有数据更危险**。补「上次值」却不打标记同样骗人：值是对的，时间是错的。
- **项目里**：采集跑着的时候杀掉从站，前 5 轮 GOOD，第 6 轮开始 **STALE，值保留 62.18 不变**，并带「上次好值 19:33:22.282」；从没读到过的判 **BAD**、显示 `--`；入库时 BAD 且无值写 **NULL** 而不是 0。
- **和新鲜度分工**：质量码是采集时对「这个值可不可信」的判定，**存进库**；新鲜度是查询时对「这条数据还活不活」的判定，**不存**。采集端挂了，库里的 quality 永远是 GOOD —— 只有新鲜度能发现。
- **告警引擎的质量码门禁**：只对 GOOD 判告警，STALE/BAD 一律不报 —— 设备掉线后那个「最后值」反复送进来，是最烦的假告警来源。
- **北向也要带**：MQTT payload 里必须带 `quality` 和 `ts`，只发一个数字，消费者分不清「刚采的」和「20 分钟前的」。
- 面试话术：「断线不能补 0。补 0 下游会把 0℃ 当真值，比没数据更危险。我的做法是值保留上次、打 STALE、带上次好值时间戳；从没读到过就是 BAD，入库写 NULL。」

### Q10. 数据新鲜度（stale/ageSeconds）是什么？和报警有什么区别？

【追问1】为什么不能在采集端判断过期？
【追问2】页面为什么要让「过期」优先于「报警」？

【简答】
`ageSeconds` = 最新点距现在多少秒，超过阈值（我们用 **15s**，采样 1s 的 15 倍）就 `stale=true`。这个判断在**查询层**做，不写进库 —— 因为只有「现在」这个时刻，才能判断「这条数据有多旧」。

【深挖】
- **为什么不能在采集端**：采集端自己挂了，就没法报告「我挂了」。
- **为什么不能在库**：时序库存的是「写进去那一刻的事实」，它不知道以后还有没有人来写；没人写，最后一条仍然是 GOOD。
- **项目里**：上线后第一次查询就抓到 10 台设备 **11764s（3 小时 16 分）**没更新，页面之前一直显示「正常」；`/api/overview` 返回 `staleDevices=10`、`staleAfterSeconds=15`，`/api/latest` 每个点位带 `ageSeconds`/`stale`，设备级「任一点位过期即过期」。
- **和报警的区别**：报警是**值越限**（业务事件，PLC 或告警引擎判）；stale 是**数据链路死了**（元数据，查询层判）。一个不动的旧值比一个报警更危险 —— 报警至少说明「设备还在说话」，过期说明「根本没人在说话」。
- **页面表现**：过期时温度**变灰**，状态列显示 `⚠ 数据过期 11764s`，并且**优先于「报警/运行/停机」**。
- **还有个更隐蔽的版本**：PLC 串口主站没勾「自动重启通信」时，通道「错误处理 = 保持最后值」会把值**冻结** —— 界面上还有数，实际早不刷新了。所以新鲜度必须靠时间戳判，不能只看「有值」。
- 面试话术：「数据库里最后一条永远是 GOOD，所以『采集端挂了』和『设备一直没变』长得一模一样。新鲜度必须在查询层算 —— 采集端和库都做不了这件事。」

### Q11. OPC UA 是什么？和 Modbus 的本质差别在哪？

【追问1】地址空间、Browse、NodeId 分别是什么？
【追问2】匿名和证书差在哪？

【简答】
OPC UA（IEC 62541）是跨系统的数据交换标准，核心不是「更快的 Modbus」，而是**信息模型 + 地址空间**：设备被抽象成对象树，变量带名字、类型、当前值，客户端可以 **Browse** 自己发现，用 **NodeId** 定位。

【深挖】
- **本质差别**：Modbus 只知道「第 3 个保持寄存器是 2 字节」，含义靠手册；OPC UA 的客户端**不看手册也能读懂** —— 快递柜编号 vs 带标签的快递。
- **容易混**：① OPC UA **不是实时控制协议**（毫秒~百毫秒），不能替代 Profinet/Modbus 做联锁；② 它也不是 SCADA 软件，是通信标准；③ 服务端不是「装了就有」，变量要**勾进符号配置并下载**才暴露。
- **项目里**：CODESYS 运行时自带 OPC UA 服务端（`:4840`）。符号配置勾了 5 个变量（`rTemp`/`xAlarm`/`rHumidity`/`wTempRaw`/`wHumidityRaw`）→ 编译 → **下载**；客户端（Python asyncua）匿名 Browse 出整棵树，读到 `rTemp=22.5`、`xAlarm=False`。
- **NodeId 长什么样**：`ns=4;|var|CODESYS Control Win V3 x64.Application.PLC_PRG.rTemp`（`ns=4` 是命名空间，后面是 `|var|设备.Application.程序.变量`）。客户端最好按名字 Browse，别硬编码 ID。
- **匿名 / 证书**：CODESYS 默认**不允许匿名**，要在「通信设置 → 设备 → 改变 Runtime 安全策略」里打开；`SecurityPolicy=None` 通道上传明文密码会被规范拒绝（`BadIdentityTokenInvalid`）。生产必须关匿名、上 `Basic256Sha256` + 客户端证书 + 符号权限 —— 我们只做到「能读通」，没做到「能上线」。
- 面试话术：「Modbus 传值，OPC UA 传带名字和类型的值。我在 CODESYS 上开了 4840，客户端匿名 Browse 就能读到 PLC_PRG.rTemp=22.5、xAlarm=False，不用点表。但匿名只是演示，生产必须关掉。」

### Q12. MQTT 是什么？QoS 0/1/2 和 retain 怎么选？

【追问1】为什么北向用 MQTT 而不是 HTTP 轮询？
【追问2】retain 是历史吗？

【简答】
MQTT 是轻量**发布订阅**协议：发布者把消息给 **Broker**（我们用 WSL2 里的 Mosquitto，1883），订阅者按 topic 收，双方互不知道对方存在。topic 是层级字符串，我们用 `iiot/{device}/{point}`。

【深挖】
- **QoS 三级**：0 至多一次（可能丢）、1 至少一次（可能重复）、2 恰好一次（四次握手，最重）。**retain** 让 broker 为每个 topic 保存最后一条，新订阅者一上线立刻拿到。
- **容易混**：① QoS2 不是「更好」是「更重」，1Hz 采集没必要；② retain 只保留**最后一条**，不是历史；③ MQTT 不是设备协议 —— 设备侧还是 Modbus，MQTT 是**北向分发**。
- **为什么不用 HTTP 轮询**：N 个消费者就是 N 组轮询，服务端压力 ×N；新消费者要等下一个周期才有数；实时性取决于轮询间隔。
- **项目里**：QoS **1** + `retain=true`；payload 带 `device/point/val/quality/ts/unit`（`ts` 是 epoch 毫秒，不用字符串，避免时区歧义）；实测发布 180 条、**0 失败**；发布端停掉后，新订阅者 `mosquitto_sub -C 1` **立刻**拿到最后一条。
- **工程约束**：北向失败不影响南向 —— `MqttPublisher.publish()` 内部 catch 掉只计数，broker 挂了不能让采集停摆。
- 面试话术：「南向 Modbus 只能问，北向 MQTT 要推。Topic 用 `iiot/{device}/{point}`，QoS1 因为工业数据丢一条可能漏一次越限，retain 让大屏/App 一上线就有数。payload 必须带质量码和时间戳。」

### Q13. SCADA / MES / EAM / CMMS 分别是什么？

【追问1】SCADA 和 MES 到底怎么分？
【追问2】你这个项目做到哪一层？

【简答】
**SCADA** 看现在（实时画面、报警、历史曲线、报表）；**MES** 管过程（工单、批次追溯、质量判定、OEE）；**EAM/CMMS** 管设备别坏（台账、保养、备件、维修工单）。三句话就够，别展开成教科书。

【深挖】
- **容易混**：SCADA 面向值班员看「现在温度多少、报警没」；MES 面向生产管理者看「这批料做了多少、良率多少、用的哪批原料」。**HMI** 是单机/单线操作屏，通常含在 SCADA 里，不等于 MES。**EAM 与 CMMS 基本是同一件事**（企业资产管理 / 计算机化维护管理），叫法不同。
- **分层（ISA-95）**：L0 现场（传感器/执行器）→ L1 控制（PLC/DCS）→ L2 监控（SCADA/HMI）→ L3 制造运营（MES）→ L4 业务（ERP）。
- **关系一句话**：ERP 决定「做什么」（订单）→ MES 决定「怎么做」（工单/工艺/追溯）→ SCADA 看「做得怎么样」（实时）→ EAM 管「设备别坏」（保养维修）。
- **项目里**：我只做到 **L2 的雏形** —— 设备列表 + 曲线 + 质量码 + 数据过期提示；**没有**工单、批次、追溯、OEE、保养计划。所以面试必须说「到 L2，不是 MES」，不能顺口说「我做过 MES」。
- 面试话术：「SCADA 看现在，MES 管过程，EAM 管设备别坏。我这个项目做到 L2 监控层 —— 往上是 MES/ERP，我没做。」

### Q14. 工业以太网 / 现场总线 / Profinet / EtherNet/IP 是什么？

【追问1】Profinet 和 Modbus TCP 是一回事吗？
【追问2】你做过 Profinet 吗？

【简答】
**现场总线**是 L1 的串行总线（Modbus RTU、Profibus DP、CC-Link、CANopen）；**工业以太网**是 L2 基于以太网的实时协议（Profinet、EtherNet/IP、EtherCAT，以及跑在 TCP 上的 Modbus TCP）。

【深挖】
- **Profinet**：西门子主导，RT 周期 1~10ms、IRT < 1ms；用**以太网帧类型 0x8892，不走 TCP/IP**，所以实时性好，但也因此需要交换机支持优先级/QoS。
- **EtherNet/IP**：罗克韦尔主导，基于 **CIP 对象模型**（对象/实例/属性），I/O 数据走 **UDP** 而不是 TCP。
- **EtherCAT**：倍福主导，报文「飞过」从站芯片时就地读写，微秒级，和上面两个不是一个实现思路。
- **容易混**：① Modbus TCP 是「以太网上的 Modbus」，10~100ms 级，不算严格意义的实时工业以太网；② Profinet 不是「西门子的 Modbus」，数据模型和实时机制都不同；③ 实时性排序：EtherCAT < Profinet IRT < Profinet RT ≈ EtherNet/IP < Modbus TCP < OPC UA。
- **项目里：没做**。我只有 Modbus RTU/TCP + OPC UA + MQTT 的实操；Profinet / EtherNet-IP 我**没有硬件、也没装过 TIA Portal**（本机 Win11 家庭版，官方只支持专业版），所以只讲概念和定位，不讲「我用过」。
- **为什么不做**：一份 demo 的边际收益低 —— 先把 Modbus 双向（主站+从站）和 OPC UA 打通，比「装个软件截图」更能证明懂协议。
- 面试话术：「Profinet 是西门子的实时以太网，不走 TCP/IP；EtherNet/IP 是罗克韦尔的 CIP，I/O 走 UDP。这两个我只有概念、没有实操 —— 我的实操是 Modbus 主站/从站双向和 OPC UA。」

### Q15. 边缘采集网关 / 上位机 / 云平台 怎么分层？

【追问1】网关和上位机有什么区别？
【追问2】你这套东西算哪一层？

【简答】
**边缘采集网关**贴着设备，负责协议转换（485/Modbus → 以太网）、断网缓存、预处理（量程校验、质量码、告警去抖）；**上位机/SCADA** 在车间或中控室，负责画面、报警、历史、报表；**云平台**在远端，负责多站点汇聚、大数据、远程运维。

【深挖】
- **容易混**：网关 ≠ 上位机（网关不画图，上位机不做协议转换）；「边缘」强调的是**就近处理**，不是「便宜的服务器」。
- **项目里**：`collector` 扮演**边缘网关** —— 南向 Modbus RTU/TCP、质量码、量程校验、批量 500 点/500ms 缓存、失败退避 1/2/4/8、断线 STALE；`platform` 扮演**上位机/SCADA 的雏形** —— 只读三个接口 + ECharts、15s 新鲜度判定；MQTT 是往**云平台**的那条路。
- **诚实的一点**：这三层现在**挤在一台 PC 上**（Windows 跑 collector/platform，WSL2 跑 TDengine/Mosquitto），物理上没分开。生产要拆：网关在车间、SCADA 在中控、云在机房，涉密网之间还要过网闸/单向隔离。
- **为什么分层值得讲**：三层失败模式不一样 —— 网关怕断网（所以要缓存 + 质量码），上位机怕卡顿（所以要只读 + 降采样），云怕丢数据（所以要 QoS + 对账）。分层不是画着好看。
- 面试话术：「我这套东西其实把三层塞进了一台电脑：collector 是边缘网关，platform 是上位机，MQTT 是上云的路。分层不是为了好听，是因为这三层的失败模式不一样。」
