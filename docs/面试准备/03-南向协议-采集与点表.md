## 〇、先把链路画在一张纸上

```
[艾克姆 IKM10000WS01]      [CODESYS 软 PLC]                 [Java 采集端]        [存储/北向]
 RS485 · COM7               Modbus RTU 主站                   TcpModbusDriver     TDengine 6041
 9600-8N1 · 从站 1    ──→   Client → Server(从站1)       ──→    FC04 读 %QW    ──→  MQTT 1883
 FC03 · 占 2 个寄存器        Channel: FC03 起始0 长度2 100ms    FC02 读 %QX         平台 8080
 offset0=湿度 offset1=温度   rTemp / xAlarm 留在寄存器          质量码 + 量程校验
```

| 端口 | 谁在监听 | 用途 |
|---|---|---|
| **1502** | `SimSlaveMain` | 仿真从站（压测与可复现实验） |
| **1503** | CODESYS | PLC 当 Modbus TCP 从站，给上位机读 |
| **4840** | CODESYS | OPC UA 服务端（见 04 篇） |
| **1883** | Mosquitto（WSL2） | 北向 MQTT |
| **6030 / 6041** | TDengine | 原生 / REST（Windows 侧只听 `[::1]`） |
| **8080** | Spring Boot | 平台页与接口 |

> 记住分工：**PLC 管「现在」，Java 管「过去」和「远方」。** 所以南向只问不推（Modbus 从站不会主动上报），北向只推不问（MQTT 发布订阅）。

### Q1. 一条数据从传感器到 TDengine，完整链路怎么走？🔴

【追问1】为什么中间要经过 PLC，Java 直接读传感器不行吗？
【追问2】每一跳的协议和端口分别是什么？

【简答】
标准形态是 **传感器 → PLC（RTU 主站）→ PLC 当 Modbus TCP 从站（1503）→ Java → TDengine**。Java 只做「搬运 + 存档」，**判断在 PLC 里做**。

【深挖】
- **L0 现场层**：艾克姆 IKM10000WS01，RS-485 接 **COM7**，**9600-8N1**，从站地址 **1**，**FC03** 读保持寄存器；**offset 0 = 湿度、offset 1 = 温度**，原始整数**×0.1** 才是工程值。（PLC 直读那一轮手上没真表，用 com0com 的 `COM5 ↔ COM6` 顶替，见 04 篇 —— 真表接回来时 COM7 只能被一个程序打开。）
- **L1 控制层**：CODESYS 里配 `Modbus_COM → Client → Server(从站1) → Channel(FC03, 起始0, 长度2, 100ms)`，PLC 自己读表、换算 `rTemp`/`rHumidity`、再判 `xAlarm := rTemp > 32.0`。
- **PLC → Java**：PLC 同时是 Modbus TCP 从站（**1503**），Java 按 `codesys.properties` 读 `%QW`（FC04 输入寄存器）与 `%QX`（FC02 离散输入）。
- **Java → 存储**：`DeviceSampler` 补质量码与量程校验 → `TdengineTelemetryRepository` 走 REST **6041** 写库，北向再发 MQTT **1883**。
- **旁路形态**：Java 也保留了直读传感器（`RtuModbusDriver` + `points-sensor.properties`）。⚠️ 但**串口是独占资源**，PLC 在线时占着口，Java 再打开同一个口直接失败 —— 「PLC 读」与「上位机直读」在物理层是**二选一**，现场才需要网关或多串口卡。
- 面试话术："我的链路是**真工业形态**：传感器进 PLC，PLC 做判断，上位机读 PLC 的结果。Java 这层不碰控制，只把『当前值』变成『历史 + 分发』。"

### Q2. DeviceDriver 抽象怎么设计的？加一个新协议要改哪里？🔴

【追问1】TCP 和 RTU 两套实现，重复代码在哪？
【追问2】加 OPC UA 要动几处？

【简答】
`DeviceDriver` 只有 `read`/`write`/`close` 三个方法，协议差异全压在实现里。**加一种协议 = 加一个实现类 + 注册表一个分支 + 点表一个 `portType`**，上层一行不改。

【深挖】
- **契约写得很硬**：`read` 返回的点**一律 GOOD**，读失败就抛 `DeviceIoException`，不许编 0 或上一次的值 —— 降级成 STALE/BAD 是采样器的职责。**驱动管协议，采样器管可信度**，这条分工是整个设计的骨架。
- **两套实现只差一个方法**：`AbstractModbusDriver.open()` 是抽象方法；`TcpModbusDriver.open()` 建 `ModbusTCPMaster`（25 行），`RtuModbusDriver.open()` 把 `SerialSettings` 翻成 j2mod 的 `SerialParameters`（72 行）；读寄存器、读线圈、解码、重连全在父类 —— 因为 j2mod 的 `ModbusTCPMaster`/`ModbusSerialMaster` 都继承 `AbstractModbusMaster`。
- **按链路复用而不是按设备**（`DriverRegistry`）：`transportKey()` 在 RTU 下是 `RTU|COM7`，TCP 下是 `TCP|<deviceId>`。不这么做，10 台 485 设备会反复打开同一个 COM 口，第二台就失败。
- **`read` 一次拿一整批点**，不是单点读 —— 批量是协议层的能力（见 Q7）；接口只给 `readOne` 的话，批量优化永远做不进驱动里。
- **如果加 OPC UA**（还没做，说清楚是设计不是现状）：新增 `OpcUaDriver implements DeviceDriver`、`DriverRegistry` 加分支、点表加 `portType=opcua` 与节点名；`DeviceSampler`/`AlarmEngine`/TDengine/MQTT **一行不改** —— 这正是当初把接口切在这里的收益。
- 面试话术："我的抽象边界是**『协议怎么读』和『数据可不可信』分开**。所以加协议只写一个 `open()`，加可信度规则只改采样器 —— 两件事永远不会互相污染。"

### Q3. 点表里到底配了什么？为什么这些必须是配置项？🔴

【追问1】少配一项会怎样？
【追问2】换一台表要改几行？

【简答】
设备级配**连法**（host/port 或 comPort/波特率/校验/从站号/周期），点位级配**语义**：`area / offset / type / order / min / max / unit / scale`。全在 `.properties` 里，代码零硬编码。

【深挖】
- **真传感器点表**（`points-sensor.properties`，节选）：

  ```
  device.sensor-01.portType=rtu  comPort=COM7  baudRate=9600  dataBits=8  stopBits=1  parity=none
  device.sensor-01.unitId=1      periodMillis=1000
  ...point.temperature.area=holding  offset=1  type=int16   scale=0.1  unit=°C   min=-40  max=80
  ...point.humidity.area=holding     offset=0  type=uint16  scale=0.1  unit=%RH  min=0    max=100
  ```

- **每项都在回答一个现场问题**：`area` 决定读 FC01/02/03/04 哪个（**四个区域编号空间独立**，配错不是数值错，是读错表）；`offset` 是**协议 0 基**，手册 40001 在这里是 0；`type` 决定占几个寄存器、怎么解；`scale` 是「整数 × 系数」的换算（`356 × 0.1 = 35.6℃`）。
- **`order` 只对 32 位类型有意义**：`PointDef.needsWordOrder()` 判 `registerCount >= 2`；16 位类型天生没有字序，要求它配 order 是「用 32 位的思维误伤 16 位」。
- **类型清单为什么必须有 INT16/UINT16**：只有 Float32/UInt32 的话，这类「整数 + 缩放」的表**一个都读不了**；温度要 `INT16` 才能表示负温，湿度用 `UINT16`（不会为负）。
- **校验前置**：`PointDef.validate()` 拦住「offset 为负」「32 位没配 order」「min > max」，`PointTableLoader` 直接抛 `IOException` —— **配错在启动时炸，不要等到现场**。
- **编码坑**：`Properties.load(InputStream)` 按 ISO-8859-1 解码，单位里的 `°C` 会乱码；所以加载器只收 `Reader`，用 UTF-8 打开文件。
- 面试话术："点表是**设备侧私有约定的落地文件**。换一台表我改一个 properties，代码不动、也不用重新编译。"

### Q4. 字序（ABCD/CDAB/BADC/DCBA）为什么必须按点位配？🔴

【追问1】配错会读出什么？
【追问2】为什么不能全局配一种？

【简答】
Modbus 只规定「寄存器是 16 位」，**不规定 32 位值怎么拆成两个寄存器**。字序是设备（甚至点位）的私有约定，必须逐点配；全局假设一种 = 把某台设备的行为当成协议标准。

【深挖】
- **四种约定**（`proto/WordOrder.java`）：`ABCD` 标准大端、`CDAB` 两字交换（国内仪表最常见）、`BADC` 字内字节交换、`DCBA` 全反。同一份报文四种解出四个数，**只有一种像温度**。
- **配错的两种后果，都要能说出来**：① **天文数字** —— 抓包里 `reg0=0xDECC, reg1=0x4278` 按 ABCD 解 ≈ **-7.36e18**（我改配置那次界面显示 **-15222668117814542000.00℃**）；② **变成 0 / 极小值** —— 另一帧 `reg0=3188(0x0C74)`、`reg1=17017(0x4279)` 按 ABCD 解 ≈ **1.88e-31 ≈ 0**。
- ⇒ **不能只靠「看着不对」发现**：程序不报错、不崩，还会若无其事标 GOOD，把垃圾一路送到页面 —— 所以必须配量程，超范围判 BAD。
- **同一台设备两种字序是允许的**：仿真从站 `temperature` 用 **CDAB**、`runtime_hours` 用 **ABCD**，一帧里共存。这就是「order 必须按点位配」的报文级理由。
- **验字序要挑带小数的值**：CODESYS 侧用 **90.1** 验出 CDAB；用 **90.0** 验不出来 —— `0x42B40000` 低位字是 0，两种解释都显示 90.00。
- **和「字节序」不是一回事**：字节序解决「4 个字节内部怎么排」，字序解决「落到哪两个寄存器、谁在前」；两者会叠加，所以做成四个正交选项，而不是一个 `bigEndian=true/false` 开关。
- **量程不是万能的**：错解出的值恰好落在区间内（62.2 变 26.2）时量程发现不了，那层只能靠和标准表比对、看曲线是不是常数 —— **别把兜底当验证**。
- 面试话术："字序错了程序不会报错，只会给你 1e18 或者 0。所以我把它做成点位级配置，再加量程兜底 —— 两层防线，缺一层就会静默出错。"

### Q5. 手册写 40001，点表为什么填 0？填 40001 会怎样？🔴

【追问1】报错长什么样？
【追问2】现场「一直超时」怎么判断是这个原因？

【简答】
`40001` 是**给人看的惯用编号（1 基）**，报文里传的是**协议偏移（0 基）**，差一位。点表填 40001，j2mod 会把它当地址直接发出去 —— 结果是**从站不响应、一直超时**，不是读到错值。

【深挖】
- **证据 1（正常读取）**：`ProbeMain` 用 `readMultipleRegisters(unitId, 0, 4)`，打印时两种编号并列：`reg[0] (40001) = 0x544E`、`reg[1] (40002) = 0x4278` —— **编号 40001 对的就是 offset 0**。
- **证据 2（真把 40001 填进去）**，同一份点表只改 `offset`：

  ```
  读失败：Executing transaction 00 05 00 00 00 06 01 03 9C 41 00 02 failed (tried 5 times)
          Socket timeout reading response - Read timed out
  从未读到过好值 → BAD（值不可用，不是 0）
  ```

  报文里那两个字节 **`9C 41` = 0x9C41 = 40001** —— j2mod 没做任何「聪明」的转换。
- **为什么是超时而不是异常码**：从站寄存器只到 offset 3，地址越界后**干脆不回包**（不同实现可能回 `02` 非法数据地址），客户端只能等超时、重试 5 次、判失败。
- **现场判据**：「地址看起来对、波特率和从站号也对，但一直超时」→ 第一嫌疑是 **1 基/0 基混了**；字序错的表现完全不同：**读得到值，但值不对**。
- **整套惯用编号**（都是 1 基、都只给人看）：`00001/10001` 线圈/离散输入（FC01/FC02）、`30001` 输入寄存器（FC04）、`40001` 保持寄存器（FC03）—— **减 1 就对了**；例外是有些手册直接给「偏移」，那照抄，别再减。
- 面试话术："Modbus 有两套编号：手册给人看的 1 基，报文里的 0 基。混了不是读错值而是永远超时 —— 这条现象比结论更有用，它直接告诉我该往哪查。"

### Q6. 32 位值跨两个寄存器，一帧里 float32 和 uint32 字序不同，怎么证明？🔴

【追问1】抓包里怎么看出来？
【追问2】怎么保证不是自己编的？

【简答】
抓包。`docs/modbus-fc03.pcapng` 是真实流量：同一帧 FC03 的 8 个数据字节里，**前两字按 CDAB 是温度、后两字按 ABCD 是运行时长**。不是推理，是逐字节对出来的。

【深挖】
- **请求（帧 9）**：`00 2f | 00 00 | 00 06 | 01 | 03 | 00 00 | 00 04` = 事务号 47、协议号 0、长度 6、从站 1、FC03、**起始 0**、**读 4 个寄存器**。
- **应答（帧 11）**：`00 2f | 00 00 | 00 0b | 01 | 03 | 08 | de cc 42 78 00 00 04 d2` = 字节数 8，`reg0=0xDECC`、`reg1=0x4278`、`reg2=0x0000`、`reg3=0x04D2`。
- **解码**：`reg0+reg1` 按 **CDAB** = `0x4278DECC` ≈ **62.2 ℃**；`reg2+reg3` 按 **ABCD** = **1234 h**。**同一帧、同一台设备、两种字序**；温度若按 ABCD 解 ≈ **-7.36e18**，一眼就知道配错。
- **事务号为什么存在**：TCP 上一条连接可能并发多个请求，靠 `Transaction Id` 配对（请求 47 → 应答 47）；RTU 一问一答串行，所以没这个字段。
- **异常应答怎么看**：功能码最高位置 1（`0x83`）+ 1 字节异常码：`01` 功能码不支持、`02` 地址越界、`03` 值非法、`04` 从站故障。**「只有请求没应答」与「回异常码」是两类完全不同的故障。**
- **抓包本身的坑**：抓包靠 **Npcap**（装了 Wireshark 不等于能抓）；回环要在装 Npcap 时勾 loopback；**Modbus/TCP 解码器默认只绑 502**，用 1502 就只显示 `data` —— 要么抓 502，要么 `tshark -d tcp.port==1502,mbtcp`（解码器名是 `mbtcp`，写 `modbus` 会报错）。
- 面试话术："排障我不只看日志。日志告诉我失败了，报文告诉我为什么失败。这一帧最能说明问题：同一帧两个点位两种字序 —— 所以字序只能按点位配。"

### Q7. 一帧读多个点位：为什么按 area 批量读？顺序怎么还原？🟡

【追问1】一个点一帧会怎样？
【追问2】寄存器数有上限吗？

【简答】
同一次采样里**按区域分组、组内取 min..max 连续范围一次读完**，再按点表顺序还原。一个点一帧会把 N 个点的采样时间拉成 N 倍，且同一批点的时刻不一致。

【深挖】
- **实现**（`AbstractModbusDriver.read`）：先按 `PointDef.Area` 分到 `EnumMap`（顺序稳定），每区域算 `firstOffset = min(offset)`、`endOffset = max(offset + registerCount)`、`count = end - first`，一次 `readMultipleRegisters` / `readInputRegisters` / `readCoils` / `readInputDiscretes`。
- **效果**：温度（offset 0，2 字）+ 运行时长（offset 2，2 字）→ **一帧 4 个寄存器**，不是两帧；湿度（offset 0）+ 温度（offset 1）→ 一帧读 2 个，`count = 2`。
- **顺序会被打乱**：分组读之后返回顺序变成「区域 A 的点 + 区域 B 的点」，与点表顺序不一致；所以最后用 `id → 下标` 的 map 重排 —— **平台侧若按位置取值，错位就是静默的数据错误**，最难查。
- **不做「部分成功」**：任一区域抛异常，**整批判失败**，不会出现「温度是新的、湿度还是上一轮」这种半新半旧 —— 宁可整批 STALE，也不给下游一批时间戳相同却可信度不同的数据。
- **上限**：RTU 报文上限 **256 字节**（地址 1 + 功能码 1 + 数据 252 + CRC 2），TCP 还要加 7 字节 MBAP 头；一次读 100 个寄存器就得拆帧 —— 合并要留上限意识。
- 面试话术："批量读不是为了快，是为了**同一批点属于同一时刻**。但合并会打乱顺序，所以我显式按点表重排 —— 顺序是契约，不能靠巧合。"

### Q8. RTU 和 TCP 的实现差在哪？🟡

【追问1】代码复用靠什么？
【追问2】串口为什么不能并发？

【简答】
**PDU 一样，外壳不一样**：RTU 加「从站地址 + CRC」走串口，TCP 加 7 字节 MBAP 头走以太网。代码上共用 `AbstractModbusDriver`，**只有建连接那一步不同**。

【深挖】
- **复用点**：j2mod 的 `ModbusTCPMaster`/`ModbusSerialMaster` 都继承 `AbstractModbusMaster`，读寄存器、读线圈、写线圈、写寄存器全在父类，所以协议逻辑抽到父类，子类只实现 `open()`。
- **RTU 三件特有的事**：① **CRC 与 3.5 字符间隔**靠 `params.setEncoding("rtu")` 交给 j2mod，自己不手算 CRC；② **串口独占**（一个 COM 口只能开一次）→ 总线上所有 `unitId` **共用一条连接**，key 用 `RTU|COM7`；③ **半双工**（发的时候不能收）→ 同一条总线的请求必须串行，公开方法都 `synchronized`。
- **`rs485Mode` 的坑**：普通 USB-485 转换器（FT232）**不要开** —— 它硬件自动切换收发方向，开了反而去调 `TIOCSRS485` ioctl，很多转换器不支持，轻则报错、重则打不开串口；只有**板载原生 485 口**才需要。
- **`echo=false`**：半双工转全双工时本地可能收到自己发出的回显字节，会让回包解析错位，建连时显式关掉，而不是指望转换器。
- **连接失效即重建**：`connection()` 每次先看 `isConnected()`，失败就 `invalidate()` 重连，不在坏连接上反复读 —— 「连上但不回包」由超时掐断，然后重建。
- **RTU 现场排查顺序**（前四项都不是代码问题）：A/B 是否接反 → 是否共地 → 波特率/校验位 → 从站地址 → 最后才是寄存器地址/字序。我在这个顺序上犯过错：A/B 还没接就扫了 16 组参数，全白扫。
- 面试话术："RTU 和 TCP 的差别主要在**物理层约束**：一个口只能开一次、只能半双工。所以我的连接管理按『链路』而不是按『设备』—— 这是串口逼出来的设计，不是我想复杂。"

### Q9. 读超时、失败重试、退避怎么做？一台设备坏了会不会拖垮全局？🔴

【追问1】为什么要退避，一直重试不行吗？
【追问2】怎么量化「隔离生效了」？

【简答】
三层隔离：**线程隔离**（每台一条虚拟线程）、**时间隔离**（读超时）、**异常隔离**（`catch Throwable`）。失败后按 **1×/2×/4×/8× 周期退避、30s 封顶**，不给掉线设备继续添乱。

【深挖】
- **退避实现**（`MultiDeviceMain.backoff`）：`shift = min(consecutiveFailures - 1, 3)`，`min(period << shift, 30_000L)` ⇒ 失败 1/2/3/4 次是 1/2/4/8 倍周期，上限 30 秒；成功一次立即清零。
- **为什么退避**：一台掉线设备继续以 1Hz 去打，只会把网络和从站拖得更慢，还把日志刷满。
- **隔离的实测证据**（20 台并发，第 8 秒直接杀掉从站进程）：

  ```
  [10:31:31]  GOOD 240/期望 240（100.00%）· STALE 0   · BAD 0
  [10:31:37]  GOOD 640/期望 720（88.89%） · STALE 80                  ← 杀从站
  [10:31:52]  GOOD 640/期望 1040（61.54%）· STALE 400 · BAD 0
  ```

- **三件事同时成立**：① **采集器没崩** —— 20 条虚拟线程全部活到 24s 收工，处理 100 轮通信失败，退出码 0；② **BAD = 0** —— 断线前都读到过好值，符合「从没读到过才是 BAD」的规则；③ **P95 从 2.15ms 恶化到 469ms、P99 到 685ms** —— 断线时连接超时拉长了延迟分布，**这才是监控该看的指标**，不是「有值就算正常」。
- **重试的边界**：**读可以重试，写不行**（见 Q11）；j2mod 内部有协议层重试（实测日志 `tried 5 times`），应用层不叠加，只做退避。
- 面试话术："我的隔离有三层：线程、时间、异常。一台设备挂掉，其他设备的数据完整率不受影响，只有它自己的点变成 STALE —— 而且我用完整率、P95、STALE 占比把这件事量化了。"

### Q10. 为什么一台设备一条虚拟线程？比平台线程省在哪？🟡

【追问1】阻塞式 IO 用虚拟线程图什么？
【追问2】有什么代价？

【简答】
Modbus 读写是**阻塞式 IO**，线程绝大多数时间在等、不在算。虚拟线程挂起时释放载体线程，一台设备一条的成本远低于平台线程，几百台也不用调线程池。

【深挖】
- **代码两行**：`Executors.newVirtualThreadPerTaskExecutor()` 提交每台设备的循环，进度线程 `Thread.ofVirtual().start(...)`；**不需要 `poolSize` 这种旋钮**。
- **省在哪**：平台线程的栈是**预留**的（默认 MB 级），几百条就吃内存、切换还要走内核；虚拟线程栈在堆上**按需增长**，阻塞（socket read / 串口 read）时**让出载体线程**去跑别人。采集端是「大量线程、几乎全在等」的典型形态，正是它的目标场景。
- **代价（要主动说）**：JDK 21 里 `synchronized` 块内的阻塞会 **pin 载体线程**，退化成平台线程。我们的读写确实 `synchronized`（485 半双工必须串行），但每次事务很短（本机回环常 <1ms），同一条链路本来就该串行，所以可接受；JDK 24 才解决 pin —— **我们跑在 21**，这点我清楚。
- **另一个易踩点**：`read` 是 `synchronized` 的，**多设备共用一个驱动实例会退化成串行**（100 台排队），所以每台一个实例：连接隔离、锁隔离、超时隔离。
- **实测规模**：`run-slave.cmd --port 1502 --devices 100` + `run-multi.cmd --fanout 100 --duration 60` 跑过 100 台共用 host/port、从站号 1..100（等价一个 485 网关后挂 100 块表）；20 台 × 24s 那组用来量化断线掉完整率。**没做长时间稳定性压测**，这点不吹。
- 面试话术："选虚拟线程不是赶时髦。采集端的瓶颈是**等待**，不是计算 —— 虚拟线程让『每设备一条线程』这个最直观的模型变便宜，我不用再维护线程池和它的队列。"

### Q11. 写操作为什么不幂等？你们怎么处理的？🔴

【追问1】FC05 写线圈不是天然幂等吗？
【追问2】那为什么还强调「读回确认」？

【简答】
Modbus 写**没有幂等保证**，超时后重发可能让执行机构**动作两次**。我们的可写点位只有线圈（置位语义，天然幂等），所以**知道这个坑、知道怎么复现，但没在代码里制造它** —— 做法是「写完读回确认，不无脑重试」。

【深挖】
- **两种真正危险的写形态**（本 demo 都没有）：① **自增/累加型**（`产量计数 += 1`）—— 重发就多计一次，数据永久错；② **触发型**（写 1 到 `CMD` 启动配方下发）—— 重发就**物理动作两遍**。
- **为什么本项目测不出来**：`motor_running` 是线圈，FC05 是**置位语义** —— 写 1 次和写 10 次结果都是 true，天然幂等，测不出「动作两次」。硬说「我测过」反而不可信。
- **要复现需要什么**：从站加 `--drop-write-ack`（真执行了但故意不回 ACK）+ 点表加一个自增型或触发型点位。
- **代码里的防线**：`DeviceDriver.write` 的 javadoc 明写「写不幂等，超时后先读回确认」；`AbstractModbusDriver.write` 失败时标记连接失效并抛出带提示的异常，**不自动重试**。实测流程是 `写线圈 FC05 → ACK=true → 读回确认 motor_running=true`。
- **读回确认不是「再读一次」**：要确认的是**语义** —— 写线圈后读回 `true` 才算成功；写设定值寄存器还要和期望值比对，不一致就报错而不是重试，因为不一致意味着「对方执行了别的动作」。
- **Modbus 里没有幂等键**：HTTP 能带 `Idempotency-Key` 让服务端去重，Modbus 报文里没有这个位置（MBAP 头只有事务号，从站也可以不认），只能靠「读回 + 状态机」在应用层补。
- **更上层的原则**：**保护/联锁永远在 PLC 里，Java 不承担控制责任**。Java 能写，但只写设定值或请求，且必须读回 —— 服务器会挂、网会断，不能让它成为安全回路的一环。
- 面试话术："HTTP 的『失败就重试』在工控里是危险的。读可以重试，写不行 —— 写超时后我不知道对方到底执行了没有，只能读回确认。这条我写进了接口注释，不是靠自觉。"

### Q12. 你怎么证明采集是对的？🔴

【追问1】除了「页面上有数」，还有什么证据？
【追问2】没有真设备的时候怎么验？

【简答】
四层证据：**抓包逐字节对** → **真传感器实测** → **仿真从站做可复现实验** → **量程校验兜底**。每一层都能指出文件和数字，不靠「看起来正常」。

【深挖】
- **① 抓包逐字节**：`docs/modbus-fc03.pcapng`（85 包 / 43 个 Modbus）；请求 `00 00 00 04` 读 4 个寄存器，应答 `de cc 42 78 00 00 04 d2` 解出 62.2℃ / 1234h —— **字节级可复算**。
- **② 真传感器实测**：艾克姆 IKM10000WS01（COM7 · 9600-8N1 · 从站 1 · FC03）—— `offset 0 = 湿度 612 → 61.2%RH`、`offset 1 = 温度 356 → 35.6℃`。⚠️ 这条还纠正了我的假设：原以为 offset 0 是温度，实测反了，点表因此改过一次。
- **③ 仿真从站做实验**：`SimSlaveMain` 用一阶低通 + 缓慢漂移 + 偶发尖峰 + 采样抖动造信号（不是 `Math.random()` 的锯齿），可复现「断线 → STALE」「杀从站 → 完整率下降」「字序改错 → 天文数字」。
- **④ 量程兜底**：`min/max` 超范围判 BAD，`DeviceSampler` 把原因写进 `lastRangeError`（提示语直接写「常见原因：点表里的 order 配错了」）。
- **⑤ 反向验证（最有说服力）**：从站 `--base-temp 25` 时点表 CDAB 读出 **25.06℃**（换量程跟着变，证明没有硬编码）；只把 order 改成 ABCD 立刻变成 **-1.52e19** —— **配置真的在驱动解码，不是摆设**。
- **⑥ 探测工具**：`ProbeMain` 一条命令扫「四个区域 × 四种字序」，看到 `253` 这种「像 25.3℃ 的整数」就说明地址对了。
- **⑦ 新鲜度**：光有值不算对，还要能回答「这个值多旧」—— 采样器记 `lastGoodAt`，STALE 值带上次好值时刻，MQTT payload 带 `ts` 与质量码。真实教训：PLC 主站超时后通道「错误处理=保持最后值」，**界面上还有数，实际已经不刷新了**，这正是「只看有没有值」会骗人的地方。
- 面试话术："我不会说『能读到数就算通』——能读到数只说明地址蒙对了。我要证明的是：字节对得上、量纲对得上、换配置会跟着变、错了能被量程拦住。"

## 二、换个问法，一句话接上

| 换个问法 | 一句话怎么答 |
|---|---|
| 你写过几行协议代码？ | 主站是自己写的（j2mod 只提供报文层）：批量合并、字序解码、连接按链路复用、退避重连都是我的代码 |
| 换个品牌的表还跑得动吗？ | 只改点表：区域、偏移、类型、字序、缩放、量程；先用 `ProbeMain` 一条命令把值扫出来 |
| 一直超时先查什么？ | 物理（A/B、共地）→ 参数（波特率/校验/从站号）→ 地址；1 基/0 基混了的表现就是「永远超时」 |
| 数据坏了怎么知道？ | 质量码 + 量程：断线是 STALE 不是 0，越界是 BAD 不是照单全收 |
| 怎么证明不是编的？ | 抓包文件、真传感器读数、从站换量程后读数跟着变 —— 三条都能复算 |
