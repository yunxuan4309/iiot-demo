### Q1. 字序配错，为什么有时解出天文数字、有时解出 0？🔴

【以为】Float32 占两个寄存器，拼一下就是值；配错顶多是个"奇怪的数"。

【其实】Modbus 只规定寄存器 16 位、**不规定 32 位怎么拆**。同一帧四解：ABCD `3.5435e+12` / CDAB **62.08** / BADC `8.9116e+08` / DCBA `1.5764e+34`。抓包那帧按 ABCD 解温度是 **-7.36e18**；而另一帧 `reg0=3188, reg1=17017` 按 ABCD 解是 **1.88e-31 ≈ 0.00**。**两个方向都会错。**

【怎么发现】不靠"看着不对"—— 程序不报错还标 GOOD。靠三条独立证据：① `ProbeMain` 四种字序并列打印；② 抓包逐字节核对（`DE CC 42 78` 按 CDAB 才是 62.2℃）；③ 同帧两点位交叉验证（温度 CDAB、运行时长 ABCD，只对一个说明是巧合）。

【怎么修】字序做成**点位级配置**（点表每个点位一个 `order`）；`WordOrder` 枚举实现四种、编解码对称；再加 `min`/`max` 量程校验，超范围判 BAD。故意把 order 改错，读出 **-15222668117814542000.00℃**，程序若无其事 —— 证明配置真在驱动解码。

【沉淀了什么】字序是设备属性、不是协议常量，同一台设备不同点位可以不同；**配错不报错**，所以"看着不对"不是检测手段，量程校验才是。

**面试话术**："这个坑最阴的是**它不报错**。我第一次看到 `1e34` 才知道拼反了，后来还遇到解出 `1.88e-31`、页面显示 0.00 的 —— 所以我不再靠肉眼，靠量程校验 + 抓包 + 同帧交叉验证。"

### Q2. 把 40001 当偏移传，为什么是"永远超时"而不是"读错值"？🔴

【以为】手册写 40001，报文里就该传 40001。

【其实】40001 是**惯用编号**（1 基，给人看的），报文传的是 **offset 0**（0 基）。真填 40001 时，从站寄存器只到 offset 3 ⇒ **地址越界 ⇒ 不响应**，客户端重试 5 次后超时。

【怎么发现】现象不是"读到错值"，而是**一直超时**：`Executing transaction 00 05 00 00 00 06 01 03 9C 41 00 02 failed (tried 5 times) / Socket timeout`。**关键就在报文那两个字节：`9C 41` = 0x9C41 = 40001** —— j2mod 老老实实把它当地址发了出去。

【怎么修】点表 `offset` 改回 `0`，同一份点表立刻正常读出 4 个点（对照组只改这一个值）。

【沉淀了什么】"一直超时"且地址"看起来是对的" ⇒ **优先怀疑 1 基 / 0 基搞混**，不是设备坏了；抓包直接看请求里的 Reference Number 两个字节。它和"FC04 返回异常码 01"要分开：**不响应 = 地址/接线/参数；回异常码 = 功能码/地址越界（有响应）**。

**面试话术**："40001 这个坑的教训是**现象会骗人**：我原以为会读错一位，实际是从站直接不响应。所以现在遇到'一直超时'，我先抓包看起始地址那两个字节，而不是先去换线。"

### Q3. 断线补 0 有什么问题？不补 0 那补什么？🔴

【以为】读不到就记 0（或记 null），反正页面有个数就行。

【其实】**0 是一个合法的测量值**。补 0 之后下游无法把它和"真的 0℃"区分开：`if (t > 80) alert()` 不触发 ⇒ 页面"一切正常"、无告警、无缺失提示，**但你什么都没采到**。

【怎么发现】采集跑着的时候把从站停掉（等于拔网线）：前 5 轮 GOOD，第 6 轮 **STALE**，值**保留 62.18 而不是变 0**，并带"上次好值 19:33:22.282"；读失败从无好值 → BAD，值显示 `--`。多设备版本同样成立：断线演练完整率 100% → **61.54%**，STALE 400、BAD 0、进程不崩。

【怎么修】每个点位保留 `lastKnown`：读失败沿用旧值 → STALE；无 `lastKnown` → BAD(NaN)；**绝不写 0**。页面把 STALE 显示成"过期/变灰"；查询层再叠加 `ageSeconds`/`stale`（15 s），解决"采集端整个挂了、库里最后一条永远 GOOD"。

【沉淀了什么】**"没有数据"和"数据是 0"是两件事**，补 0 是把故障伪装成正常；质量码管"采到时可不可信"，新鲜度管"现在还新不新"，**两者互补、缺一不可**。

**面试话术**："补 0 是把故障伪装成正常。我的做法是**值可以是旧的，但必须标'这是旧的'** —— 用 STALE + 上次好值时刻，再在查询层算数据有多旧。宁可明确地'不知道'，也不给一个看起来正常的假值。"

### Q4. 一台设备卡死，为什么会拖垮整轮采集？🔴

【以为】一台设备慢，最多它自己慢，不影响别人。

【其实】"连上但不回包"要**卡满整个超时**才报错；而 `read()` 是 `synchronized` 的，多台设备共用驱动实例时 100 台会**退化成串行** —— 一台卡死，全队等它。

【怎么发现】从站加 `--hang-unit 2 --hang-after 5`：TCP 连接不断、就是不回包（报文永远组不出来）。3 台实测：卡死那台单轮 **12,875.79 ms**，同期另两台 **1.2~2.6 ms** —— 延迟没有传导，但卡死那台自己拖了很久。

【怎么修】**四重隔离 + 退避**：线程隔离（每台一条虚拟线程）、连接/锁隔离（每台独立 `TcpModbusDriver` 实例）、时间隔离（读超时 2000 ms，"连上不回包"也会被掐断）、异常隔离（设备循环 `catch (Throwable)`）；失败退避 **1×/2×/4×/8×**，上限 **30 s**。

【沉淀了什么】**"连接被拒"是快速失败（几毫秒放弃）；"连上不回包"才真正拖垮采集** —— 后者才是现场最难查的。10 台版量化：完整率 **99.28%**（STALE 8 / BAD 0）、吞吐 **37~38 点/秒**、通信失败只 **2 轮**（退避生效）、问题设备清单点名 `sim-05`；100 台版 **388.3 点/秒**、P50 **1.27 ms** / P99 **9.95 ms**、0 失败。

**面试话术**："单设备拖垮采集，根因不是'设备慢'，是**共享了阻塞资源**。我做的是线程/连接/时间/异常四重隔离，再加失败退避 1-2-4-8。实测一台卡死，另两台还是 1~2 毫秒，采集器跑完正常收工 —— 一台设备只能影响它自己。"

### Q5. TDengine 明明起来了，为什么 Java 连不上、curl 却能通？🔴

【以为】`localhost` 能连就行；curl 通了，Java 的 HTTP 客户端也该通。

【其实】WSL2 的端口转发**只监听 IPv6 回环 `[::1]`**：`netstat` 显示 `[::1]:6041 LISTENING`；`http://127.0.0.1:6041` 连不上，`http://[::1]:6041` 返回 200。Java `HttpClient` **默认偏好 IPv4** ⇒ 解析到 127.0.0.1 ⇒ `ConnectException`；而 `curl.exe` 会自动回退 IPv6 —— **"curl 能通"不代表"Java 能通"**。

【怎么发现】同一台机器上 curl 成功、Java 报连接异常；再单独试 `127.0.0.1` 失败、`[::1]` 成功 ⇒ 定位到地址族，不是服务端。

【怎么修】给 JVM 加 `-Djava.net.preferIPv6Addresses=true`，URL 保持 `localhost`（推荐，URL 可读）；或 URL 直接写 `http://[::1]:6041`。

【沉淀了什么】**"客户端 A 能连、客户端 B 连不上" ⇒ 第一时间查地址族和监听地址**，不要怀疑服务端；端口约定要写进交接文档（6030/6041 只监听 `[::1]`）；这类问题日志里只有一句 `ConnectException`，不查 `netstat` 会查很久。

**面试话术**："这个坑的通用价值是**别用'另一个客户端能通'来证明服务端没问题**。curl 会自动回退 IPv6、Java 默认偏 IPv4，所以一个通一个不通。我先看 `netstat` 的监听地址，一眼看到只有 `[::1]` —— 加个 JVM 参数就好了。"

### Q6. TDengine 服务端在 Windows 上装不了，最后为什么装进了 WSL2？🔴

【以为】TDengine 支持 Windows，下个 exe 装服务端就行；或者跑官方 `install.sh` 最省事。

【其实】官方 CDN 上**只有 client 的 Windows 包**，`server` 的 Windows 包**全 404**（同版本 Linux 包 200，178.5 MB），下载页 HTML 里连 "Windows" 字样都没有。`install.sh` 会往 `/usr/local/taos`、`/etc/taos`、`/var/lib/taos` 写东西并注册 systemd ⇒ **要 root**。真正的二进制在**两层的包**里：外层 `install.sh` + `package.tar.gz`，里面才是 `bin/cfg/inc`。

【怎么发现】先探 URL（server 404 / Linux 200 / client 200）；解包后 `ls` 才看到 `package.tar.gz` 里才是二进制。

【怎么修】免 root 部署到 `$HOME`：解 `package.tar.gz`；给 `libtaos.so` / `libtaosnative.so` **建软链**（`taos` 缺 `libtaos.so` 报 `error while loading shared libraries`，`taosadapter` 缺 `libtaosnative.so` 会**秒退、日志无有用信息**）；写 `taos.cfg` + `taosadapter.toml`（**`-c` 要文件不是目录**；日志键是 **`[log] path`** 不是 `logPath`，写错会被静默忽略、回落 `/var/log/taos` 报 permission denied）；`setsid nohup` 起进程；Java 走 **REST 6041**、零第三方依赖。

【沉淀了什么】**"能不能装"要先用 URL/文档验证**，别凭"印象中支持 Windows"排计划；taosAdapter 的坑几乎都在**配置键名**上（错了不报错，只是行为不对）；端口都 >1024 ⇒ 普通用户可监听，**不需要 sudo**。

**面试话术**："TDengine 没有 Windows 服务端包，我踩的第一个坑就是**先信了'应该支持'**。后来学乖了，先探 URL 再动手。最后方案是 WSL2 里免 root：解压到 home、自己建 `.so` 软链、写好两个配置；Java 走 REST，不装任何 native 库。"

### Q7. 时间戳写进去、读出来差了 8 小时，是哪一层错了？🔴

【以为】写进去什么时间，读出来还是什么时间；最多是"设备时钟有点漂"。

【其实】第一个撞到的不是时钟漂移，是**时区**。采集端写的是 **epoch 毫秒**（数字、不带时区，本地约 11:23），TDengine **按 UTC 存**，查询返回带 `Z` 的 ISO 串：`2026-10-24T03:23:19.306Z` ⇒ 本地 UTC+8 ⇒ **差 8 小时**。

【怎么发现】把"写入时的本地时刻"和"查出来的串"并排对比，看到 `Z` 才反应过来是 UTC。更隐蔽的版本：只显示 `HH:mm:ss` 时看不出日期差，**跨零点的数据会错位到前一天**。

【怎么修】四层各管一段：采集端 **epoch 毫秒写入**（不传字符串时间）；存储 UTC（不可改，这是对的做法）；后端 UTC ISO **原样透传、不本地化**（不该假设客户端在哪个时区）；前端 `new Date(iso)` 交给浏览器转本地时区。

【沉淀了什么】**"时间"要分三层看：设备时钟、存储时区、展示时区** —— 混在一起就是"数据看起来晚 8 小时"这种查一整天的问题。还没做的：设备侧 **NTP 对时**、乱序/迟到数据处理（真设备到货后才有的问题）。

**面试话术**："时间这个坑我是从时区撞进去的：库里存 UTC、返回带 Z，前端不转就整张图偏 8 小时。我的做法是**传输层统一 UTC，只在展示层转本地** —— 后端一旦本地化，就再也说不清原始时刻了。"

### Q8. Wireshark 装了，为什么 tshark 抓不了、也抓不到 127.0.0.1？🔴

【以为】装了 Wireshark 就能抓包，网卡列表里自然有回环。

【其实】**Wireshark 本体 ≠ 抓包驱动**：抓包靠 **Npcap**，winget 静默装 Wireshark 时不一定带上 ⇒ `tshark -D` 报 `Unable to load Npcap (wpcap.dll)`。Npcap 安装时 **「Support loopback traffic」默认不勾** ⇒ 网卡列表没有回环，**抓不到 127.0.0.1 的流量**。

【怎么发现】`tshark -D` 报错 → 查 `Get-Service npcap` 不是 Running；装完再看 `tshark -D`，要能找到 `\Device\NPF_Loopback`。

【怎么修】单独装 Npcap（npcap.com）并**勾上 loopback**；装完确认 `Get-Service npcap` 是 **Running**；抓回环用 `tshark -i \Device\NPF_Loopback -f "tcp port 502" -a duration:8 -w docs\modbus-fc03.pcapng`。

【沉淀了什么】**工具链要验到"能产出证据"这一步**，不是"装完就算"；抓包是**南向排障的最终证据**（功能码、起始地址、从站真没回还是回了异常码）；结果是可复查的（85 个包、43 个 Modbus，落在 `docs/modbus-fc03.pcapng`），不是"我记得当时……"。

**面试话术**："我以为装了 Wireshark 就有抓包能力，结果 tshark 直接报找不到 `wpcap.dll` —— 抓包驱动是 Npcap、独立组件。第二个坑更隐蔽：Npcap 默认不勾 loopback，127.0.0.1 根本抓不到。这两个都不难，是**工具链没验到能出证据那一步**。"

### Q9. 抓包里全是 data、Modbus 过滤 0 帧，为什么？🔴

【以为】只要报文是 Modbus，Wireshark 就能自动认出来。

【其实】**Modbus/TCP 解码器默认只绑 502 端口**。我们用 **1502**（避开特权端口），它不自动识别 ⇒ 全部显示 `data`、`modbus` 过滤 **0 帧**。

【怎么发现】过滤 0 帧；换 502 抓立刻能解；再试 `-d tcp.port==1502,mbtcp` 也能解出功能码。

【怎么修】三选一：① **抓的时候就用 502**（最省事，本次采用）；② `tshark -d tcp.port==1502,mbtcp` —— **解码器名是 `mbtcp`**，写 `modbus` 会报 `Protocol "modbus" isn't valid for layer type "tcp.port"`；③ GUI 右键 → **Decode As** → Modbus/TCP。

【沉淀了什么】**`-d` 只把解码器挂到端口上，解码器内部还要靠端口号区分方向**（请求 → 502 是目的，应答 → 502 是源）⇒ 绑了 1502 仍会报 **"Cannot classify packet type"**。要方向正确就用 GUI 的 Decode As（同时设双向），或直接抓 502；**"过滤 0 帧"不等于"没有 Modbus 流量"**，先怀疑解码器、再怀疑抓包位置。

**面试话术**："这个坑有两层：第一层是 Modbus 解码器只认 502，我用 1502 就全是 data；第二层是就算用 `-d` 绑上，它还要靠端口判断请求/应答方向，所以仍报无法分类。结论是**要么抓 502，要么用 GUI 的 Decode As**。"

### Q10. CODESYS 串口主站配好了却一直超时，问题在一个默认值？🔴

【以为】按手册填 9600-8-N-1 就行，新建的串口主站默认应该是对的。

【其实】CODESYS 的串口主站新建时，**校验位默认是 `EVEN`**，而传感器是 `NONE`。表现是：**连接建立成功、但每次读都超时**，没有任何"校验错"的提示。

【怎么发现】状态页只有超时、没有异常码；拿传感器手册逐项核对主站参数，才发现校验位是 EVEN（8E1）而不是 NONE（8N1）。

【怎么修】改一处：**`奇偶校验 → 无`**，其余（9600 / 8 / 1 / 从站 1）不变。

【沉淀了什么】**"超时"不等于"没接对"**：接线、地址、波特率、校验位，任何一项不对都表现为超时，所以必须逐项核对；**默认值也是配置**，工具给的默认值不代表你的设备；和 RTU 那次连起来 —— **排障顺序 = 物理 → 电平 → 参数 → 数据**，校验位属于"参数"层。

**面试话术**："这个坑很典型：连接是通的、报文也发了，就是每次读都超时，而且没有任何报错。最后发现是串口主站的校验位默认 EVEN，我的表是 8N1。**默认值不是对的，是要核对的。**"

### Q11. 主站/从站加反了，怎么配都不出数？🔴

【以为】设备树里带 "Modbus" 字样的，加一个上去就能读。

【其实】CODESYS 里有两个长得很像的东西：**`Modbus Serial Device` = 服务器/从站**（等着别人来读）；**`Modbus Client, COM Port` = 客户端/主站**（主动去读别人）。我一开始加的是前者，**方向反了**，所以怎么配都不出数。

【怎么发现】配完一直没数据；回头看设备描述里的 Client / Server 字样，才发现加的是"服务器"。

【怎么修】删掉重加，正确层级：`Modbus_COM (Modbus COM) → Modbus_Client_COM_Port（主站）→ Modbus_Server_COM_Port（描述对端传感器，地址 1）→ Channel：FC03 · 起始 0 · 长度 2 · 周期 100ms`。

【沉淀了什么】**先定"谁是主站"，再选设备**：这条链里 PLC 要主动读传感器 ⇒ PLC 是 Client/主站；**中文翻译反直觉**（Modbus 的"主站 = Client、从站 = Server"），按英文名和描述判断，别按中文"主/从"的字面感觉；同类坑：Modbus TCP 的 `Modbus TCP 主站` 描述也是 "works as a Modbus **Client**"。

**面试话术**："我加错了设备类型：`Modbus Serial Device` 是服务器/从站，`Modbus Client, COM Port` 才是主站。Modbus 的中文'主/从'和设备树里的'服务器'很容易反，我现在的习惯是**只看英文 Client/Server 和描述**。"

### Q12. PLC 停机后，为什么界面上还有数、但其实已经不刷新了？🔴

【以为】对端重启/拔线之后，主站会自己恢复；就算不恢复，值至少会变 0 或报错。

【其实】主站超时后**停在错误态**，通道的 **「错误处理 = 保持最后值」** 把值**冻结** —— 界面上看起来还有数，实际已经不刷新。另外 `Application` 停止后，要**手动"启动"**（不会自动跑）。

【怎么发现】拔掉 COM7（或重启对端）：CODESYS 里 `rTemp` **保持最后值**、`xAlarm` 不动；状态页能看到通道错误；设备树里 `Application [停止]` 时服务端根本不启动。平台侧值不变，但**时间戳变旧**。

【怎么修】通道勾 **「自动重启通信」**，让主站超时后自行恢复、不靠人重连；`Application` 停止后手动"启动"或 `在线 → 登录`；**平台侧不信任"有值"** —— 用时间戳算 `ageSeconds`，超 15 s 标过期，这才看得出"冻结"。

【沉淀了什么】**"有值"不等于"在刷新"** —— 这正是数据新鲜度必须靠时间戳、不能只看"有没有数"的原因；**通信要能自愈**，现场没人会守着点"重新连接"；这类"冻结"比断线更难发现（断线页面会空，冻结页面看起来完全正常）。

**面试话术**："PLC 停机后主站停在错误态，通道的'保持最后值'把数冻住了 —— 界面上还有数，其实早不刷新了。所以我一要勾'自动重启通信'让它自愈，二要平台侧按时间戳判过期。**'有值'不等于'在刷新'**，这句话在现场很值钱。"

### Q13. OPC UA 匿名被拒、填了用户名密码还是被拒，为什么？🔴

【以为】客户端连上服务端就能读；填个 admin + 密码总比匿名更保险。

【其实】CODESYS 默认**不允许匿名** OPC UA 连接（设备用户管理开着）⇒ `ActivateSession` 被拒、返回 **`BadIdentityTokenInvalid`**。改用用户名 + 密码，asyncua 打印 `Sending plain-text password`，服务端**仍然拒** —— 因为客户端走的是 **SecurityPolicy = None** 通道，而 OPC UA 规范**禁止**在无加密通道上传明文密码。

【怎么发现】返回码是 `BadIdentityTokenInvalid`（不是网络错、不是超时）；客户端日志里有 `Sending plain-text password`；再对照"当前通道是 None"。

【怎么修】**演示**：`通信设置 → 设备 → 改变Runtime安全策略 → 勾「允许匿名登录」` → 确定（写到 PLC，必要时重启）。**生产**：关匿名，配 **`Basic256Sha256` + 客户端证书**，并把客户端证书导入 PLC 信任列表。

【沉淀了什么】**"能读通"和"能上线"是两件事**，匿名只是把链路验证出来；**安全策略和身份认证是一对**（None 通道只能匿名，要用户名密码就得上加密通道）；还有个小坑：SP22 把 OPC UA 设置挪到了**通信设置页顶部的「设备」下拉菜单**里（叫"改变Runtime安全策略"），不在 Device 的标签页里。

**面试话术**："OPC UA 我踩了两个连着的坑：默认不让匿名，报 `BadIdentityTokenInvalid`；改用用户名密码还是被拒 —— 因为通道是 None，规范禁止传明文密码。所以演示阶段我开匿名把链路跑通，生产必须换成 Basic256Sha256 + 证书。"

### Q14. OPC UA 里明明有变量，为什么 Browse 不到？🔴

【以为】变量写在 PLC 程序里，OPC UA 服务端就应该能看到。

【其实】**只有勾进「符号配置」的变量才会暴露**；而且符号配置**不是普通源码**，勾完编译还不够，**必须随下载（或在线修改）传送到 PLC** 才生效。

【怎么发现】符号配置里打了勾、也编译了，客户端 Browse 仍没有任何 `PLC_PRG` 变量；再看编辑器顶部那行灰字：**"变更的符号配置将同下一个下载或在线修改传送"** —— 提示已经写在那儿了。

【怎么修】四步（实测有效的顺序）：`Application` 右键 → 添加对象 → **符号配置**（勾"支持 OPC UA 特征"）→ 勾选要暴露的变量（`rTemp`/`xAlarm`/`rHumidity`/`wTempRaw`/`wHumidityRaw`）→ **编译** → **在线 → 登录（下载）**。下载后 `DeviceSet → <plc> → Resources → Application → ...` 下才长出变量节点。

【沉淀了什么】判据要明确：**下载后 Browse 树里有没有 `PLC_PRG.*`**，而不是"我勾过了"；**没勾 = 不暴露**，这本身就是最朴素的安全边界（按最小权限勾选）；OPC UA 与 Modbus 的本质差别也在这里 —— 能 Browse 出名字/类型/值的树，Modbus 只能靠人配偏移（"带标签的快递" vs "快递柜编号"）。

**面试话术**："变量看不到，我第一反应是服务端没起来，其实是**符号配置没下载**。它不是源码，改完必须下载或在线修改才生效。现在我的判据很硬：下载后 Browse 树里有没有 `PLC_PRG.rTemp`。"

### Q15. GX Works2 里一条 `CMP` 为什么死活转换不了？梯形图还有哪些反直觉？🔴

【以为】梯形图是画布：元件能拖、指令放哪儿都行、监视模式下能直接改值。

【其实】三条都不对：裸的无触点指令（`CMP`/`MOV`）**没有通断状态**，不能直接挂母线，GX Works2 会把它推到行末、压到右母线 ⇒ F4 报 **「存在无法转换的梯形图」**；**元件不能拖**（位置 = 指令在梯级里的顺序）；**监视模式只读**（标题栏写着「(只读)」）。

【怎么发现】F4 反复失败、方框永远贴最右边；想拖 CMP 拖不动；监视时在图上打不进字、双击 `D0` 弹出的是"搜索"。

【怎么修】在 `CMP` 前面挂一个触点，通常用 **`LD M8000`**（FX 的常 ON 特殊继电器）当母线入口；改顺序 = 删掉按目标顺序重输，**全程键盘、别点鼠标**（一点光标就跑，梯级会被拆成两个断头）；改值走 `调试(B) → 当前值更改(M)` → 填值 → **「设置」**（值空着时按钮是灰的）。

【沉淀了什么】**梯形图软件是指令序列编辑器，不是画图工具** —— 顺序就是执行顺序；`M8000` 的两个经典用途 —— **给无触点指令做母线入口**、**做上电初始化**；颜色：GX Works2 用**蓝色**表示导通（CODESYS 才是绿色），照"变绿"去找会以为没生效；同类坑还有中文输入法把 `>` 转全角，`LD>` 被拆成 `LD`，出现 `-|K0|` 怪接点。

**面试话术**："GX Works2 让我明白梯形图不是画布：元件不能拖、裸 `CMP` 会被推到右母线报'无法转换'，得先 `LD M8000` 给它一个母线入口；监视模式是只读的，改值要走'调试→当前值更改'。这些都是**软件的模型和直觉不一致**，不是装坏了。"

### Q16. CODESYS 占着串口，Java 为什么打不开同一个 COM 口？🔴

【以为】CODESYS 能读传感器，我的 Java 程序也能同时读同一个 COM 口 —— 各读各的。

【其实】**串口是独占资源**。CODESYS 在线时占着 COM7（改造初期是 COM5），Java 再打开同一个口**直接失败**；现场一台设备的 485 口通常也只接一个主站。

【怎么发现】Java 打开串口报错（不是超时，是打不开）；把 CODESYS 的串口连接停掉，Java 立刻能打开。

【怎么修】不是"修 bug"，是**改架构**：让 **PLC 当 Modbus RTU 主站直读传感器**（`%IW10/%IW11`），Java 退到"只读 PLC 的 Modbus TCP 1503"。改造后实测：`wTempIn=0`（Java 没参与）、`wTempRaw=356`、`rTemp=35.6`、`xAlarm=TRUE`。要多主站共享一条 485，现场得用**网关或多串口卡**。

【沉淀了什么】**"PLC 读"和"上位机读"在物理层就是二选一** —— 这是真实工业约束，不是代码 bug；改造顺带把架构改成了**真实产线形态**（现场设备先接 PLC，PLC 采集与判断，上位机再去读 PLC）；和坑 4 的"连接/锁隔离"一个道理 —— **共享的物理资源必须显式设计归属**，不能假设"大家都能开"。

**面试话术**："串口独占这个坑让我改了架构：原本是 Java 直读传感器、再写进 PLC，看起来能演示，但**方向和真实产线相反**。后来我让 PLC 当 RTU 主站自己读，Java 只读 PLC —— `wTempIn=0` 就是证据，说明 Java 真的没参与采集。"

## 讲这些坑的方法（比坑本身更重要）

1. **先讲现象，再讲根因**：面试官要听"你怎么发现的"，不是"你背了多少知识"。
2. **每个坑给一个可验证的判据**：报文里的 `9C 41`、`[::1]:6041`、`Application [停止]`、Browse 树里的 `PLC_PRG.rTemp` —— 有判据才像真做过。
3. **主动说边界**：`--hang` 是自己造的故障、终端电阻没实测、软 PLC 不是硬 PLC。**说清边界比装成全能安全。**
4. **落到"沉淀了什么"**：坑讲完要落到一条可复用规则（量程校验、四重隔离、按依赖顺序排障），否则就只是"我遇到过一个怪问题"。
